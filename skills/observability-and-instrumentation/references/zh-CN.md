# 可观测性完整手册（中文）

给代码埋点、让生产行为可见可诊断的完整方法论。动手加任何遥测前必读。
英文版为 `references/playbook.md`，两个版本的方法论、阈值与检查表完全一致，仅语言不同。

---

## 1. 概述

你无法观测的代码，就是你无法运维的代码。可观测性，是仅凭代码发出的遥测信号、
从外部回答"系统在做什么、为什么这么做"的能力。埋点不是上线后再补的插件 ——
它和功能同时写出来，就像测试一样。如果一个功能发出去却没有任何遥测，
那么第一个用户报上来的缺陷就成了一次考古，而不是一次查询。

---

## 2. 适用场景

- 构建任何要跑在生产环境的功能
- 新增服务、接口、后台任务或外部集成
- 一次生产事故排查耗时过长（"我们查不出到底发生了什么"）
- 搭建或评审告警规则
- 评审一个引入了 I/O、重试、队列或跨服务调用的 PR

**不适用于：**

- 正在排查一个此刻正在发生的故障 —— 用 `debugging-and-error-recovery` 技能
  （可观测性决定那个技能下次能有多快）
- 对已经测量出来的慢做性能剖析与优化 —— 用 `performance-optimization` 技能
- 上线当天的监控检查清单与回滚触发条件 —— 见 `shipping-and-launch` 技能；
  本技能覆盖的是喂给它们的那些埋点

---

## 3. 第 1 步 —— 埋点之前先定义"正常工作"

没有问题的遥测就是噪声。在加任何埋点之前，先写下 2–4 个运维工程师会针对这个功能提出的问题：

```
功能：结算支付重试
运维会问的问题：
1. 多大比例的支付是首次就成功，多大比例是重试后才成功？
2. 支付最终失败时，原因是什么？（供应商报错？超时？校验不通过？）
3. 支付供应商是不是比平时慢？
→ 下面每一个信号都必须有助于回答其中一个问题。
```

如果你说不出这些问题，说明你还没准备好埋点 —— 你会把什么都记下来，然后什么也没学到。

要把问题写在运维工程师能找到的地方：这个功能的 runbook、覆盖该功能的 ADR，
或者遥测初始化代码上方的注释。没人能找到的问题，凌晨三点只能靠猜来回答。

---

## 4. 第 2 步 —— 为每个问题挑对的信号

| 信号 | 回答什么 | 成本特征 | 示例 |
|---|---|---|---|
| **结构化日志** | "这个具体case发生了什么？" | 按事件计；随流量增长 | `payment_failed`，带供应商错误码 |
| **指标** | "整体上多频繁 / 多快？" | 按序列固定；查询便宜 | 供应商调用的 p99 延迟 |
| **追踪** | "跨服务的时间花在哪了？" | 按请求计；通常采样 | 一次慢结算，按跳拆分 |

经验法则：指标告诉你**出事了**，追踪告诉你**在哪出的事**，日志告诉你**为什么出的事**。

成本特征决定了选型。按事件计的信号（日志）在高流量下既昂贵又无用；
基数固定的聚合（指标）始终便宜，也是唯一能可靠告警的东西。
如果问题是"多频繁"，那它就是指标 —— 而不是一条让人凌晨三点去 grep 的日志。

## 5. 第 3 步 —— 结构化日志

记录事件，而不是散文。每一条日志都是一个 JSON 对象，带有稳定的事件名和机器可读的字段：

```typescript
// 差：字符串拼接 —— 不可查询、前后不一致
logger.info(`Payment ${id} failed for user ${userId} after ${n} retries`);

// 好：稳定的事件名 + 结构化字段
logger.warn({
  event: 'payment_failed',
  paymentId: id,
  provider: 'stripe',
  errorCode: err.code,
  attempt: n,
}, 'payment failed');
```

**日志级别 —— 要始终一致地使用：**

| 级别 | 含义 | 运维动作 |
|---|---|---|
| `error` | 不变量被破坏；可能需要有人介入 | 排查 |
| `warn` | 已降级但已处理（重试成功、走了兜底） | 观察趋势 |
| `info` | 重要业务事件（下单、任务完成） | 无 |
| `debug` | 诊断细节 | 生产环境默认关闭 |

**关联 ID 是强制的。** 在系统边界生成（或接收）一个请求 ID，并把它附加到每一条日志、
每一个 span 和每一次出站调用上。没有它，你无法从交错的日志里重建出一次请求：

```typescript
// Express：每个请求一个子 logger，ID 向下游传播
app.use((req, res, next) => {
  req.id = req.headers['x-request-id'] ?? crypto.randomUUID();
  req.log = logger.child({ requestId: req.id });
  res.setHeader('x-request-id', req.id);
  next();
});
```

上游有 ID 时就接受它，没有时才生成 —— 否则链路会在你的边界处断掉，
上游每一跳都成了孤儿。

**当多个入口往同一个日志汇里写时，要标注入口。** 关联 ID 能标识一次运行，
却不能说明是哪条代码路径启动了它。同一个任务被调度器、被重放接口、被手工 CLI 触发时，
会在同一个日志汇里产生可以互换的日志行，于是归因只能退化为排除法 ——
去交叉比对调度器历史、进程表、部署日志 —— 而这套论证只在那些外部记录恰好还存在着的时候成立。
在运行的起点、紧挨着关联 ID 的位置盖上入口标记，并用同样的方式把两者一起传播下去：

```typescript
// 所有入口共用一个辅助函数：这次运行自己的 logger 同时带上两个字段。
// 用 `entryPoint` 而不是 `source` —— ECS 把 `source.*` 保留给了网络字段。
export const runLog = (entryPoint: 'scheduler' | 'replay_endpoint' | 'cli', runId: string) =>
  logger.child({ entryPoint, requestId: runId });

// 调度器触发        -> runLog('scheduler', crypto.randomUUID())
// POST /jobs/:id/replay -> runLog('replay_endpoint', req.id)
// CLI 调用          -> runLog('cli', process.env.RUN_ID ?? crypto.randomUUID())
```

这两个字段必须跨越与关联 ID 相同的边界 —— 队列元数据、HTTP 头 —— 否则工作进程会去重新推导入口，
然后靠猜。一个只是与入口相关的字段是提示，不是归因：任何能调用这个任务的东西都能复现它。

**绝不记录密钥、token、密码或完整的 PII。** 这是来自 `security-and-hardening` 技能的硬性规则 ——
遥测管道是一条经典的数据泄露路径。对字段采用白名单；不要记录整个请求体。

```typescript
// 用白名单，不要用黑名单：只有这些字段会进入日志汇
const safeFields = (user: User) => ({ userId: user.id, plan: user.plan });
// 绝不：logger.info({ user }) —— 整个对象连带 token 都会落进日志汇
```

## 6. 第 4 步 —— 指标

对于请求驱动型服务，在**每个端点**和**每个外部依赖**上埋 **RED**：
**R**ate（每秒请求数）、**E**rrors（失败率）、**D**uration（延迟**直方图**，不是平均值）。
对于资源（队列、连接池、主机），使用 **USE**：**U**tilization（利用率）、
**S**aturation（饱和度）、**E**rrors（错误）。

和追踪一样，厂商中立的路径是 OpenTelemetry 的指标 API（与第 5 步同一个 SDK 和同一套 context）。
下面的示例用的是 Prometheus 的 `prom-client` —— 一个常见的后端选择，不是唯一选择；
无论用哪个后端，RED/USE 与基数规则都完全一样。

```typescript
import { Histogram } from 'prom-client';

const httpDuration = new Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP request duration',
  labelNames: ['method', 'route', 'status_class'],  // '2xx'，而不是 '200'
  buckets: [0.05, 0.1, 0.25, 0.5, 1, 2.5, 5],
});
```

**基数是失效模式。** 每一种唯一的标签组合都是一条独立的时间序列。
标签必须来自小的固定集合（路由模板、状态类、供应商名）。
绝不要把用户 ID、原始 URL、错误消息或其他无界的值当作标签 —— 那些属于日志和追踪。

```
可以当标签：  route="/api/tasks/:id"   status_class="5xx"   provider="stripe"
绝不当标签：  user_id、email、request_id、完整 URL、错误消息文本
```

永远不要用平均值，永远用分位数：平均值会掩盖那 1% 体验极差的用户。
用直方图，读 p50/p95/p99。

**命名约定让指标可被找到：** 时长用 `_seconds` 后缀，计数器用 `_total` 后缀，
使用基本单位（秒、字节）而不是毫秒、千字节，并把单位写进名字里，
这样写仪表盘的人永远不需要猜。

## 7. 第 5 步 —— 分布式追踪

用 OpenTelemetry —— 它是厂商中立的标准，而且自动埋点几乎零代码就能覆盖 HTTP、gRPC
和常见数据库客户端：

```typescript
// tracing.ts —— 必须在任何其他模块之前导入
import { NodeSDK } from '@opentelemetry/sdk-node';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';

const sdk = new NodeSDK({
  serviceName: 'checkout-service',
  instrumentations: [getNodeAutoInstrumentations()],
});
sdk.start();
```

只在有意义的内部工作单元周围加手动 span（例如 `applyDiscounts`、`chargeProvider`），
并附上运维会用来筛选的属性。跨每一个异步边界传播 context —— HTTP 头、队列消息元数据 ——
否则链路会在缺口处断掉。默认用低比例的头部采样；如果后端支持尾部采样，错误保留 100%。

"必须在任何其他模块之前导入"是字面意思：自动埋点是在导入时给模块打补丁的，
所以如果 `tracing.ts` 在 HTTP 客户端注册之后才被导入，就没什么可打补丁的了，
链路会空空如也，而且任何地方都不会报错。

## 8. 第 6 步 —— 告警

对**用户能感知到的症状**告警，而不是对原因告警：

```
症状（值得叫人）：                    原因（放仪表盘，不要叫人）：
错误率 > 1% 持续 5 分钟               CPU 85%
p99 延迟 > 2s                         某个 pod 重启了
队列积压 > 10 分钟                    磁盘 70%
```

基于原因的告警会在什么问题都没有的时候响，又会漏掉你没预判到的故障。
基于症状的告警恰好在用户被伤害时才响，无论原因是什么。

你创建的每一条告警都要遵守的规则：

1. **必须可行动。** 如果标准回应是"忽略它，它会自愈"，那就删掉这条告警。
2. **链接到一份 runbook** —— 哪怕只有三行：它意味着什么、第一条该跑的查询、升级路径。
3. **有阈值和持续时长**，且由 SLO 或历史数据支撑，而不是拍脑袋。
4. 只用两级严重度：**page**（用户可见，立即处理）和 **ticket**（降级，本周处理）。
   第三层会变成噪声，把人训练成什么都不看。

持续时长正是"叫人"与"抖动噪声"的分界线：阈值被突破一个采集周期是噪声，
同一个阈值持续五分钟才是信号。这个窗口要从 SLO 的错误预算里取，
或者从历史上该状况自愈需要多久来取。

## 9. 第 7 步 —— 验证遥测本身

埋点也是代码；它同样可能写错。在宣布收工之前，触发这些路径，亲眼看一看真实输出：

- 在预发强制制造一个错误 → 用 `requestId` 在日志里找到它，确认字段是结构化的（不是 `[object Object]`）
- 打一点测试流量 → 确认指标序列以预期的标签和合理的值出现了
- 在追踪 UI 里跟着一个请求穿过各个服务 → 没有断掉的 span
- 每条新告警各触发一次（临时调低阈值）→ 确认它到达了正确的渠道，且 runbook 链接可用

最后这一项检验才是真正要紧的：**在预发注入的故障，必须只靠遥测就能定位，不需要读源码。**
如果你必须打开代码才能理解发生了什么，那说明埋点还不完整。

## 10. 常见借口对照表

| 借口 | 现实 |
|---|---|
| "等它跑通了我再加日志" | "之后"会变成"第一次事故之后" —— 那是发现自己瞎了的最贵时刻。边写边埋。 |
| "日志越多 = 可观测性越好" | 非结构化的噪声只会让事故排查更慢，不是更快。三条可查询的事件胜过三百行散文。 |
| "先用 console.log 也行" | 非结构化输出没法过滤、没法关联、没法告警。结构化 logger 一次性多花五分钟。 |
| "出问题的时候我们看仪表盘就行" | 没有围绕明确问题搭建的仪表盘，会给你看一切，唯独不给答案。从运维问题出发。 |
| "重要的都告警，以后再调" | 一个吵闹的寻呼机把人训练成无视它。调优永远不会发生，漏掉真实告警一定会发生。 |
| "把用户 ID 做成指标标签更好排查" | 它也会让你的指标后端崩掉。高基数查询属于日志和追踪。 |
| "我们才两个服务，上追踪是过度设计" | 两个服务就已经存在日志回答不了的跨服务延迟问题。自动埋点让成本低到可以忽略。 |
| "有关联 ID 就足以归因一次运行了" | 它标识的是这次运行，不是入口。三个调用方往同一个汇里写时，归因会退化成在明天可能就不存在的记录之间做排除。 |

## 11. 危险信号

- 一个引入了重试、队列或外部调用的功能 PR，却没有任何新的遥测
- 日志行是用字符串拼接出来的，而不是结构化字段
- 没有关联 ID / 请求 ID —— 每条日志都是孤儿
- 一个日志流同时由调度器、webhook 和手工运行写入，却没有字段说明是哪一种产生的
- 指标用用户 ID、原始 URL 或错误消息文本做标签（基数炸弹）
- 延迟只记了平均值，没有任何分位数
- 告警天天响，被确认一下就完事，没有任何动作
- 对原因（CPU、内存）告警去叫人，而用户可见的错误率却无人监控
- 日志里出现密钥、token 或完整的请求体
- "我机器上能跑"是证明一个生产功能健康的唯一证据
- 追踪初始化代码被放在它本该去插桩的那些库之后才导入
- 一条没有 runbook 链接的告警

## 12. 验证清单

给一个功能做完埋点之后，确认：

- [ ] 这个功能对应的运维问题已写下来，且每个信号都能映射到其中一个
- [ ] 所有日志输出都是结构化的（JSON），事件名稳定，且每一行都带关联 ID
- [ ] 每个被多个入口写入的日志汇都带有入口字段，在运行的起点设置，并随关联 ID 一起传播，而不是在下游推断
- [ ] 任何日志行里都没有密钥、token 或未脱敏的 PII（要抽查真实输出）
- [ ] 每个新端点和每个外部依赖都有 RED 指标，且标签集合有界
- [ ] 延迟是直方图；p95/p99 可查询
- [ ] 一次请求能在追踪 UI 里被端到端跟下来，没有断掉的 span
- [ ] 每条新告警都是基于症状的、有 runbook 链接，并且各试触发过一次
- [ ] 在预发注入的故障，是仅靠遥测定位到的，不需要读源码

### 上线前埋点门禁

上面这份清单的速查版，作为功能发布前必须清掉的门禁：

- [ ] 运维问题已写下且可被找到（runbook / ADR / 初始化代码注释）
- [ ] 每条新路径都有结构化日志，带关联 ID 与入口字段
- [ ] 每个新端点和外部依赖都有 RED 指标
- [ ] 每个新队列、连接池或资源都有 USE 指标
- [ ] 标签被限制在小固定集合内；任何地方都没有高基数标签
- [ ] 延迟直方图就位；没有任何指标是平均值
- [ ] 追踪最先初始化，context 跨每个异步边界传播
- [ ] 已定义基于症状的告警，带阈值、持续时长与 runbook 链接
- [ ] 仅两级严重度 —— page 与 ticket
- [ ] 遥测端到端验证过：注入的错误能用 `requestId` 找到、span 未断、告警试触发过
- [ ] 任何发出的载荷里都没有密钥或完整的 PII
