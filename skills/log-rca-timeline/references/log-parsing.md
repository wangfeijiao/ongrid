# 日志解析与时间窗口聚合规范

本文件规定「原始日志 → 可统计的时间序列」这一步的全部口径。**统计口径不统一，后面的异常检测与根因排序全部失效**，因此这一步优先于任何归因动作。

---

## 一、输入形态与自动识别

`analyze_logs.py` 按文件逐行嗅探格式，命中即切换解析分支：

| 形态 | 识别判据 | 抽取方式 |
|---|---|---|
| **JSONL** | 前 120 个非空行中 ≥ 80% 以 `{` 开头且可 `json.loads` | 按字段名直取 |
| **CSV** | 首行含逗号 ≥ 2 个，且存在 time/date/ts/level/msg 类表头 | 表头映射，列数不符则退化为位置映射 |
| **纯文本** | 其余情况 | 正则抽时间戳 + 关键词抽级别/耗时/服务名 |

判定失败时不会抛错，而是落到纯文本分支继续尝试——**宁可降级解析，不要直接失败**。

### 1.1 字段名映射表（不区分大小写）

- 时间：`ts` `timestamp` `time` `@timestamp` `datetime` `date` `logtime` `log_time` `occur_time` `event_time` `created_at` `asctime` `t`
- 级别：`level` `levelname` `severity` `loglevel` `log_level` `lvl` `priority`
- 耗时：`rt` `latency` `duration` `duration_ms` `cost` `cost_ms` `elapsed` `took_ms` `time_ms` `response_time` `resp_time` `spend` `elapsed_ms`
- 服务：`service` `svc` `app` `application` `module` `component` `logger` `source` `pod` `host` `hostname` `container` `appname`
- 正文：`msg` `message` `log` `content` `text` `body` `detail` `event`

字段名不在表中时，用 `--input` 之外的别名机制无法生效，需先做一次字段重命名（`jq`/`awk`/自家采集端改配置），**不建议在分析脚本里硬塞项目专有字段名**。

## 二、时间戳解析

按下列顺序尝试，全部失败则丢弃该行并计入未解析率：

1. ISO8601 / 常见变体：`2026-09-28 10:00:00`、`2026-09-28T10:00:00.123`、`2026/09/28 10:00:00`（可带 `Z` 或 `±HH:MM`）
2. nginx / Apache：`28/Sep/2026:10:00:00`
3. Android logcat：`09-28 10:00:00.123`（需 `--assume-date`）
4. syslog：`Sep 28 10:00:00`（需 `--assume-date`，年取当前年或指定年）
5. Unix epoch：10 位（秒）或 13 位（毫秒），自动判别
6. 仅时分秒 `10:00:00`：**必须** `--assume-date 2026-09-28` 才解析，否则丢弃

### 2.1 三个必须注意的坑

- **跨时区混排**：脚本检测到 `Z` 或 `±HH:MM` 会在 `flags` 中提示。多机房日志建议在采集侧统一为 UTC，否则「同一条时间线」本身就是错的。
- **日志自身时间 vs 采集时间**：优先用日志正文时间（业务发生时刻）。用采集时间会把采集延迟算进故障时长。
- **时间回拨**：NTP 校时或容器时钟漂移会造成时间倒退。脚本按时间戳排序后聚合，回拨样本会被归入较早窗口，需在 `flags` 中人工确认。

### 2.2 解析率红线

- ≥ 95%：可直接采信
- 90%–95%：结论可用，但需在 `flags` 说明
- < 90%：**先修解析再归因**。未解析的行往往正是格式最特殊的异常行（堆栈行、多行异常），漏掉它们会系统性低估错误量。

## 三、时间窗口选择

### 3.1 auto 规则

`span / window_size <= 80` 满足即取该粒度，阶梯为：
`10s → 30s → 1m → 5m → 10m → 15m → 30m → 1h → 3h → 6h → 1d`

### 3.2 按故障类型手工选粒度

| 故障特征 | 建议粒度 | 理由 |
|---|---|---|
| 连接池瞬时打满、GC 停顿 | 10s–30s | 分钟粒度会把尖峰平滑掉 |
| 接口错误率抬升、依赖抖动 | 1m–5m | 与常见监控告警粒度对齐 |
| 内存泄漏、磁盘增长、容量类 | 15m–1h | 看趋势不看尖峰 |
| 跨日复盘、周同比 | 1h–1d | 控制窗口数量 |

**粒度选择的原则：让「异常」在图上占据至少 2–3 个窗口**。只占 1 个窗口的异常无法与其相邻窗口形成对比，稳健 z 会因 MAD 被抬高而漏检。

### 3.3 空窗处理

区间内无日志的窗口**不跳过**，补零保留。理由：零窗口是「断流」这一模式唯一的证据来源；一旦跳过，断流就永远检测不到。

## 四、聚合指标定义

每个时间窗输出以下字段（见 `data.json` 的 `buckets`）：

| 字段 | 定义 | 用途 |
|---|---|---|
| `total` | 窗口内日志总条数 | 流量体量，也是「日志量突增」的唯一依据 |
| `TRACE/DEBUG/INFO/WARN/ERROR/FATAL` | 按级别计数 | 分级占比、级别结构突变 |
| `errors` | `ERROR + FATAL` | 错误量绝对数 |
| `error_rate` | `errors / total` | **跨窗口可比的错误强度**，比绝对数更稳健 |
| `p50 / p95 / p99` | 窗口内耗时字段分位数 | 延迟抬升、长尾恶化 |
| `top_sig` / `top_sig_share` | 最高频日志签名及其占比 | 重试风暴、单点集中的直接证据 |
| `top_svc` / `top_svc_share` | 日志量最高的服务及占比 | 定位范围收敛 |
| `z_*` | 各序列的稳健 z 值 | 异常判据的核心输入 |

### 4.1 日志签名（signature）归一化

同一类错误必须归到同一个签名，否则「错误签名数」会被 ID 噪声淹没。归一化顺序：

1. UUID → `<uuid>`
2. 长十六进制（≥16 位，含 traceId/spanId）→ `<hex>`
3. IP（含端口）→ `<ip>`
4. 引号内文本 → `<str>`
5. 数字 → `<n>`
6. 路径（含 ≥2 段斜杠）→ `<path>`
7. 截断至 180 字符

示例：

```
原始：handle orderId=88231 failed, trace=4f2a...c1, cost=3120ms, ip=10.2.3.4:8080
签名：handle orderId=<n> failed, trace=<hex>, cost=<n>ms, ip=<ip>
```

**注意**：不要过度归一化。把 `timeout` 和 `refused` 都归一成 `<str>` 会直接丢掉根因线索——只归一化「变量部分」，保留「语义部分」。

### 4.2 耗时的单位陷阱

文本抽取规则：`rt=/cost=/took=/elapsed=/duration= / latency=` 后跟数字，单位 `ms` 原样、`s` ×1000、`us` ÷1000、**无单位按 ms 处理**。

无单位时按毫秒是**约定而非事实**。若日志里 `cost=3` 实际是 3 秒，P95 会被低估 1000 倍。首次分析某套日志时，务必用一条已知耗时的请求反查一次单位。

## 五、解析失败与降级路径

| 现象 | 处置 |
|---|---|
| 完全解析不出时间戳 | 检查是否需 `--assume-date`；确认时间戳是否在行尾或用了非标准分隔符 |
| 级别字段抽不到 | 脚本按正文关键词兜底（error/exception/fail → ERROR；warn/timeout/retry/slow → WARN），应在 `flags` 提示「级别为推断值」 |
| 服务名抽不到 | 文本模式取首个方括号且跳过级别名与线程名；仍失败则记为 `-`，此时「单服务集中」模式自动失效 |
| 多行堆栈 | 目前按行处理，堆栈行通常无时间戳而被丢弃；建议在采集侧合并为单行（`multiline` 配置），否则错误量被低估 |
| 文件超大 | 默认上限 200 万行；超出需先按时间切片，或改在采集端做预聚合 |

## 六、可复现性要求

一次分析要能被复盘，必须记录并随交付物保留：

1. 输入的**文件清单**与每个文件的行数、解析率
2. **窗口粒度**与聚合区间（起止时间）
3. 本次使用的**非默认参数**（`--window` / `--start` / `--end` / `--assume-date` / `--changes` / `--alert`）
4. 分析脚本版本（`SKILL.md` 的 `version`）

`analyze_logs.py` 已将 1–3 项写入 `data.json` 的 `meta`，第 4 项由交付时一并说明。
