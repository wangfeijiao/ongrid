# 故障时间线规范与复盘要点

时间线的价值在于**把散落在不同系统里的时刻对齐到同一条轴上**：日志、指标、变更、告警、处置动作。对齐之后，「谁是因、谁是果」通常一目了然。

---

## 一、阶段划分（七个阶段）

| 阶段 | 判定方式 | 记录内容 |
|---|---|---|
| **观察起点** | 分析窗口的第一个时间窗 | 窗口粒度、覆盖范围、数据完整性 |
| **潜伏** | 首个高严重度模式之前存在低/中严重度模式或零星异常线索 | 早期征兆（慢查询、零星超时、池水位抬升）——**这是最有改进价值的一段** |
| **触发** | 高严重度模式的起始窗口 | 形态、涉及服务、峰值、样本日志 |
| **放大** | 影响量最大的窗口 | 峰值错误率、峰值错误量、扩散到的服务 |
| **发现** | 用户提供的告警时刻（可选） | 用于计算 MTTD |
| **缓解 / 恢复** | 异常结束后连续 3 个窗口错误率 ≤ 基线 1.5 倍且未断流 | 恢复判定的依据必须写清，否则「恢复时刻」会变成主观判断 |
| **观察终点** | 分析窗口末尾 | 是否仍在观察期、是否需要延长监测 |

**潜伏段是复盘的核心资产**：如果从潜伏到触发有 20 分钟而监控毫无反应，改进项就是「把 pool waitCount / 慢查询 / GC 停顿纳入告警」。

## 二、事件记录规范

每个事件必须包含六个字段：

| 字段 | 要求 |
|---|---|
| `t` / `t_label` | 精确到秒（窗口级事件标注窗口起始） |
| `phase` | 七阶段之一 |
| `title` | 一句话，动词开头，不带情绪 |
| `detail` | 关键数值（峰值、基线、倍数、持续时间） |
| `source` | 数据来源：`聚合` / `模式识别` / `用户提供` / `变更记录` |
| `severity` | 高 / 中 / 低 |

### 2.1 写法要求

- 时间统一到**同一时区**，并在文档头部声明（建议 UTC+8 或 UTC 二选一，全篇一致）
- 使用**业务时间**（请求发生时刻），不要用采集时间或入库时间
- 数值必须带单位与比较基准：「错误率 12.4%（基线 0.3%）」，不要只写「错误率很高」
- **不写推测**：推测内容放入「根因假设」章节，时间线只放事实
- 同一时刻多个事件都要保留，用 `kind` 区分（`anomaly` / `peak` / `change` / `alert` / `recover`）

### 2.2 常见错误

| 错误 | 后果 |
|---|---|
| 只记录「故障开始」和「故障结束」 | 无法复盘，等于没记 |
| 把处置动作与故障事件混在同一条 | 无法区分「系统自己恢复的」和「被人救回来的」 |
| 用人工回忆的时间 | 与日志/指标对不上，会把因果判反 |
| 漏掉变更记录 | 变更类根因永远排不上来（这是最常见漏项） |
| 恢复时刻取「最后一个错误」 | 应取「连续 3 窗回到基线」，否则会把偶发抖动当未恢复 |

## 三、指标口径

| 指标 | 定义 | 说明 |
|---|---|---|
| **MTTD**（Mean Time To Detect） | 告警时刻 − 首个异常窗口 | 需用户提供告警时刻；未提供时本技能不臆测 |
| **MTTR**（Mean Time To Recover） | 恢复窗口 − 首个异常窗口 | 脚本按「连续 3 窗回到基线」判定恢复 |
| **影响时长** | 最后一个异常窗口结束 − 首个异常窗口 | 与 MTTR 略有差异：不要求已恢复 |
| **影响窗口数** | 落入异常区间的窗口个数 | 用于折算受影响请求量（乘窗口平均 QPS） |
| **峰值错误率** | 异常区间内最大 `error_rate` | 反映最坏时刻的强度 |

**口径必须写在交付物里。** 同一个故障，用「最后一个错误」和用「连续 3 窗回到基线」算 MTTR，可能相差十几分钟。

## 四、复盘清单（无责复盘）

### 4.1 事实层

- [ ] 时间线是否覆盖潜伏 → 触发 → 放大 → 缓解 → 恢复全段
- [ ] 是否包含变更记录（发布、配置、扩缩容、DDL、证书轮换、网络变更）
- [ ] 关键指标是否取自真实数据源（不是人工回忆）
- [ ] 是否区分「系统自愈」与「人工干预」

### 4.2 分析层

- [ ] 根因假设是否逐条给了验证动作与排除条件
- [ ] 是否存在未被解释的高严重度异常模式（有遗漏说明分析不完整）
- [ ] 是否区分了触发因 / 放大因 / 暴露因
- [ ] 排序第一的假设，如果用 3 分钟就能验证，为什么当时没验证

### 4.3 改进层

- [ ] 每条改进项是否有负责人、截止时间、验收标准
- [ ] 是否包含**缩短 MTTD** 的项（新告警、阈值调整、看板补齐）
- [ ] 是否包含**缩小影响面**的项（限流、熔断、隔离、退避、降级）
- [ ] 是否包含**防止复发**的项（回归用例、灰度策略、变更审批）
- [ ] 改进项是否有跟踪机制，能否在下次复盘时核销

### 4.4 文化层

- [ ] 表述是否对人不对事（禁止「某某疏忽导致」）
- [ ] 是否奖励了「发现者」而不是只追究「引入者」
- [ ] 复盘结论是否对全员公开（可脱敏，但不应只在小圈子留存）

## 六、与其他技能的衔接

- 需要**纯数值序列的统计体检**（离群点、变点、自相关、游程）→ 用 `timeseries-anomaly-radar`，本技能聚焦原始日志文本的解析与归因。
- 需要**单段日志文本的即时解读**（粘贴一段堆栈问怎么回事）→ 可直接对话，本技能适合有文件、有时间跨度的场景。
- 需要**把复盘写成正式文档**（Word/腾讯文档）→ 交付后按团队模板二次排版。
