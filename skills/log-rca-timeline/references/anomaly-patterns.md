# 异常模式库（14 类）

异常检测分两层：**先做稳健统计判定「这个窗口不正常」**，**再按形态判据判定「这是哪一类异常」**。两层都通过才输出模式，避免把噪声包装成结论。

---

## 一、统计底座：为什么用中位数 + MAD

- **均值 + 标准差**在故障场景下会被异常点自身抬高（掩蔽效应：异常越多，阈值越高，越检测不到）。
- **中位数 + MAD**（绝对中位差）在异常占比 < 50% 时几乎不受污染，是 SRE 场景的标准选择。
- 稳健 z：`z = (x - median) / (1.4826 × MAD)`。判定阈值 `|z| ≥ 3.5`。
- **两遍法**：第一遍用全量算 median/MAD，剔除 `|z| ≥ 3` 的点后重算，用第二遍的基线做最终判定。这一步对「故障占了窗口 1/3」的长故障尤其重要。
- **MAD = 0**（序列几乎恒定，如全程 0 错误）时不能直接判分母为 0：脚本退化为「与中位数有差异即给 ±6 的饱和 z」，避免漏检首个错误。

### 1.1 双阈原则

只满足 z 值不输出模式，必须同时满足**幅度阈**：

| 序列 | z 阈 | 幅度阈 |
|---|---|---|
| 日志量 | ≥ 3.5 | ≥ max(5, 2 × 基线) |
| 错误条数 | ≥ 3.5 | ≥ max(5, 3 × 基线) |
| P95 耗时 | ≥ 3.5 | ≥ max(2 × 基线, 基线 + 100ms) |

理由：基数为 1 的序列出现 3 也能拿到很大的 z，但业务上毫无意义。**双阈是控制误报率最有效的一招。**

## 二、14 类模式

### 高严重度（优先处置）

**1. `traffic_spike` 流量突增**
- 判据：`total` 稳健 z ≥ 3.5 且 ≥ 2 × 基线
- 形态：日志量整窗抬高，常伴随错误量同向上升
- **必做区分**：真实流量放大 vs **日志放大**。重试循环、循环打印、DEBUG 开着都会造成「日志量涨但业务量没涨」。验证：比对入口 QPS。
- 反例：批量任务、定时对账、全量同步的固定时段都会稳定触发，若与历史同时段一致则属正常，应改看「同比」而非「环比」。

**2. `traffic_drop` 流量断崖 / 断流**
- 判据：`total` ≤ max(25% × 基线, 1) 且 z ≤ −3.0
- 形态：整窗日志量塌陷
- **必做区分**：业务挂了 vs 采集挂了。若业务 QPS 同步下降 → 真故障；若业务正常 → 采集侧断流（agent 死、磁盘满、队列丢包）。
- 反例：上游限流导致请求根本没进来，业务侧「静默正常」，此时要看网关侧指标。

**3. `error_burst` 错误率飙升**
- 判据：`errors` z ≥ 3.5 且 ≥ max(5, 3 × 基线)
- 形态：错误量成倍抬高，`error_rate` 同步上升
- 输出会附 `top_sig`（最高频错误签名）与 `rate`（窗口错误率），这是根因排序的主要输入

**4. `fatal_spike` 致命错误突现**
- 判据：`FATAL` ≥ 3 且 > max(3 × 中位数, 2)
- 形态：FATAL/PANIC/OOMKilled 类日志成簇出现
- 语义：通常直接对应**进程退出、OOM、不可恢复异常**，是最高优先级的形态

**5. `retry_storm` 重试风暴**
- 判据：同一签名单窗口 ≥ 50 次且 ≥ max(5 × 上一窗口, 30)
- 形态：同一签名高频重复，逐窗放大
- 常见来源：客户端重试无退避、补偿任务反复触发、消息重复投递、死循环
- 危害：会**放大**下游压力，把局部故障变成全局故障

**6. `cascade` 级联传播**
- 判据：≥ 2 个服务的错误起始窗口存在 ≥ 2 个窗口的先后差
- 输出：`chain` 字段给出「服务 → 首次恶化偏移窗口数」序列
- **治理原则**：处理最早恶化的一环，后续多为被拖垮方
- 反例：多服务同时因同一基础设施（网络、DNS、机房）故障而同时恶化 → 起始时间差 < 2 窗口，不会判为级联，应改看基础设施假设

### 中严重度

**7. `latency_climb` 延迟抬升**
- 判据：P95 z ≥ 3.5 且 ≥ max(2 × 基线, 基线 + 100ms)
- 需先确认「全局抬升」还是「个别接口抬升」，后者才指向具体依赖

**8. `slow_p99` P99 长尾恶化**
- 判据：同窗口内 `P99 ≥ 3 × P95`
- 语义：多数请求正常、少数极慢。常见于 GC 停顿、个别下游抖动、锁等待、冷启动
- 与 `latency_climb` 的区别：前者是整体平移，后者是长尾断裂

**9. `new_error_pattern` 新错误签名涌现**
- 判据：本窗口内此前从未出现的错误签名 ≥ 2 个，且占本窗口错误签名 ≥ 50%
- 语义：**新代码路径 / 新依赖被触发**，是「近期变更」假设最强的形态证据
- 注意：首窗（i < 2）不判定，否则会因「冷启动全是新签名」误报

**10. `concentrate_service` 单服务集中**
- 判据：某服务占窗口错误 ≥ 70%
- 语义：把定位范围从「整个系统」收敛到「一个组件」，是最高效的一条线索

**11. `step_shift` 阶跃 / 持续漂移**
- 判据：后半段中位数 ≥ 2 × 前半段中位数（日志量或错误率），且差值有业务意义
- 语义：**形态是台阶而不是尖峰**，指向配置生效、容量变化、慢性泄漏、开关切换
- 反例：数据量自然增长（用户增长、日切）也会造成台阶，需与历史同期比较

**12. `saturation` 饱和度线索**
- 判据：命中池/内存/磁盘/队列类关键词（`pool exhausted`、`too many connections`、`queue full`、`rejected execution`、`OOM`、`full GC`、`no space left`、`lag`、`backlog`）
- 语义：USE 方法中的**饱和度**信号，须与资源指标交叉验证
- 注意：这是**线索**而非结论，日志里出现「pool」不代表池是根因，可能只是它的下游先崩了

**13. `silent_gap` 日志静默**
- 判据：连续 ≥ 2 个非首尾窗口零日志
- 语义：**优先怀疑采集侧**；若业务指标同步下降，则静默本身就是故障表现（进程假死、OOM 被杀、容器被驱逐）

### 低严重度

**14. `periodic_glitch` 周期性毛刺**
- 判据：≥ 3 个异常窗口且间隔变异系数 CV < 0.35，**且平均间隔 ≥ 2 个窗口**（后一条用于排除「连续异常」被误判为周期）
- 语义：定时任务、健康检查、批处理、对账作业、GC 周期
- 处置：先确认是否属预期；预期内的应从告警中排除，预期外的查调度配置

## 三、误报控制清单（交付前自查）

1. **窗口数量 < 12**：基线不可靠，任何 z 值都应降权看待
2. **粒度掩盖尖峰**：只占 1 个窗口的异常容易漏，改小粒度重跑
3. **业务周期未剥离**：日切、大促、批处理时段必须与历史同期对比
4. **日志放大干扰**：日志量类模式必须先确认业务量是否同步变化
5. **堆栈多行丢失**：错误量被系统性低估，`error_rate` 偏低
6. **采集时间替代业务时间**：故障时长被采集延迟污染
7. **同一根因重复计数**：多个模式实际上是同一件事的不同切面（如 `error_burst` + `concentrate_service`），不做合并会显得"异常很多"

## 四、从模式到假设的映射

模式本身不是结论，它是**约束条件**。每条根因假设必须解释得通至少一类高严重度模式，否则该假设缺乏形态支撑。

| 模式 | 最可能指向 |
|---|---|
| `error_burst` + `cascade` | 依赖故障、基础设施故障 |
| `latency_climb` + `saturation`（pool 类） | 连接池/线程池耗尽 |
| `fatal_spike` + `saturation`（OOM/GC 类） | 内存溢出、GC 停顿 |
| `new_error_pattern` + `step_shift` | 近期发布/配置变更 |
| `traffic_spike` + `latency_climb` | 外部流量突增、缓存击穿 |
| `retry_storm` + `concentrate_service` | MQ 重复投递、客户端无退避重试 |
| `silent_gap` 单独出现 | 日志采集侧异常 |
| `periodic_glitch` | 定时任务、健康检查、批处理 |

**一个模式可以支持多个假设，一个假设通常需要多个模式共同支撑。** 排序逻辑见 `references/rca-ranking.md`。
