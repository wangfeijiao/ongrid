# 日志根因定位（Log RCA Timeline）

把一段时间跨度的日志，变成一份**可复盘的故障时间线**和一份**可验证的根因假设排序**。

---

## 它解决什么问题

线上故障时，最耗时的往往不是修，而是**找**：

- 日志几十万行，翻到眼花也说不清「到底几点开始不对」
- 错误日志一堆，但分不清哪条是**因**、哪条是**果**
- 复盘会上各执一词：「我觉得是数据库」「我觉得是发布」，谁都没有证据

本技能的做法是：**先把日志按时间窗口聚合成可比较的统计序列**，让「异常」变成一个可以量化的偏离（而不是感觉），再按形态识别出这是哪一类异常，最后对候选原因打分排序，并明确告诉你**先验证什么、什么情况下可以划掉它**。

---

## 交付物

一次运行产出三份东西：

| 文件 | 内容 |
|---|---|
| `data.json` | 全部原始结论：聚合序列、异常模式、根因假设、时间线、分析局限 |
| `report.html` | 可视化看板：聚合序列图、异常模式摘要、根因假设排序、故障时间线 |
| `render_check.txt` | 看板自检报告（用于确认渲染无异常） |

看板是**单文件 HTML**，无外部依赖，可直接发给同事、贴到复盘文档里。

---

## 快速开始

把日志文件（或整个日志目录）交给技能，说清「分析这段时间的日志，找根因」即可。默认参数会自动选择窗口粒度。

想手工控制时：

```bash
python -X utf8 scripts/analyze_logs.py \
    --input /path/to/logs --glob "*.log" \
    --window 1m \
    --changes /path/to/changes.txt \
    --alert "2026-09-28 10:47" \
    --title "订单服务故障分析" \
    --out ./rca_run/data.json

python -X utf8 scripts/build_board.py ./rca_run --out report.html
```

### 支持的日志形态

- **纯文本**：`2026-09-28 10:00:00 [ERROR] [order-service] ...`
- **JSONL**：`{"ts":"2026-09-28T10:00:00","level":"ERROR","service":"order-api","rt":3120,"msg":"..."}`
- **CSV**：含 `time/level/msg` 类表头

时间戳自动识别：ISO8601、nginx/Apache（`28/Sep/2026:10:00:00`）、syslog（`Sep 28 10:00:00`）、Android logcat、Unix epoch（秒/毫秒）。只有时分秒的日志需 `--assume-date YYYY-MM-DD` 补日期。

### 能抽出来的字段

级别（`ERROR/WARN/INFO` 等，抽不到时按关键词推断）、耗时（`rt=` `cost=` `took=` `duration=` 或 JSON 的 `rt/latency/duration`）、服务名（JSON 字段或 `[service]` 括号，自动跳过级别名与线程名）。

**耗时单位约定**：`ms` 原样、`s` ×1000、`us` ÷1000、**无单位按毫秒处理**。首次分析某套日志时建议用一条已知耗时的请求反查一次。

## 识别哪些异常

十四类模式，按严重度分档：

**高**：流量突增、断崖/断流、错误率飙升、致命错误突现、重试风暴、级联传播
**中**：延迟抬升、P99 长尾恶化、新错误签名涌现、单服务集中、阶跃/持续漂移、饱和度线索、日志静默
**低**：周期性毛刺

判定用**两遍法「中位数 + MAD」稳健 z**（抗异常污染）配**双阈**（z 阈 + 幅度阈，控制误报）。

### 三组最容易搞错的区分（本技能会明确提示）

1. **真实流量放大 vs 日志放大**——日志量涨了，业务量未必涨。重试循环、循环打印、DEBUG 全开都会造成「日志暴涨」。必须比对入口 QPS。
2. **业务故障 vs 采集断流**——日志断流了，业务未必挂。若业务 QPS 正常，问题在采集侧（agent 死、磁盘满、队列丢弃）。
3. **首发环节 vs 被拖垮环节**——级联传播里，最早恶化的一环才是治理重点。

## 根因排序怎么来的

```
形态覆盖度 40% + 证据强度 28% + 时序吻合 14% + 形态先验 10% + 集中度 8% − 惩罚项
```

- **证据分级**：直接证据（`OOMKilled`、`pool exhausted`、`no space left`、`deadlock found`）＞ 强相关（时间吻合 + 集中度）＞ 弱线索
- **时序硬约束**：线索晚于效应出现的，判为次生现象并降权
- **置信度**：A ≥ 65 分，B 40–64 分，C 一般不输出

候选因库 14 条，每条都带**具体验证动作**与**可排除条件**。例如：

> 假设「连接池/线程池耗尽」——验证动作：看池的 active / idle / waitCount 曲线，确认获取连接的等待耗时是否先于错误率抬升；**可排除条件**：池始终有空闲、等待数为 0。

「可排除条件」是判断一条分析是否专业的试金石：**写不出排除条件的，就不是假设，是猜测。**

## 重要说明

- **结论是假设排序，不是定论。** 日志能证明「发生了什么、在哪里、什么时候」，不能证明「为什么」。所有假设都必须与监控指标、调用链、变更记录交叉核对。
- **未提供告警时刻时不会臆测 MTTD**；未提供变更记录时不会给变更类假设加时序满分。
- **多行堆栈按行处理**：堆栈行通常无时间戳会被丢弃，建议在采集侧开启 multiline 合并，否则错误量会被系统性低估。
- **日志不是全知视角**：静默的配置变更、上游未记录的重试、网络设备丢包，这些日志里根本没记录的原因，本技能排不出来。
- **敏感数据**：日志常含手机号、身份证、令牌、内网地址。脚本只做统计与截断展示（每条样本截 180–220 字符），不会整理成清单。交付前请确认脱敏与保密边界。
- **不执行处置动作**：不下发修改、不重启服务、不改配置。只输出验证动作与修复方向。

## 目录结构

```
log-rca-timeline/
├── SKILL.md                        技能主说明（工作流、口径、字段规范）
├── manifest.yaml                   上架元数据
├── icon-512.png                    技能图标
├── references/
│   ├── log-parsing.md              解析与时间窗口聚合规范
│   ├── anomaly-patterns.md         十四类异常模式判据与误报控制
│   ├── rca-ranking.md              证据分级、打分公式、候选因库
│   └── timeline-postmortem.md      时间线规范与复盘清单
├── scripts/
│   ├── analyze_logs.py             日志 → data.json（核心引擎）
│   ├── build_board.py              data.json → report.html
│   ├── render_check.js             看板自检（含最小 DOM 桩渲染）
│   ├── selfcheck.py                技能包自检（--e2e / --log）
│   └── gen_icon.py                 图标生成
└── assets/
    └── board_template.html         看板模板
```

## 自检

```bash
# 静态检查
python -X utf8 scripts/selfcheck.py

# 完整链路（日志 → data.json → 看板 → 渲染自检）
python -X utf8 scripts/selfcheck.py --log /path/to/sample.log
```
