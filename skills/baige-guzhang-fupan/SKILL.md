## 用途

把一次故障的"碎片材料"（告警记录、聊天记录、口述回忆）变成**一份能沉淀经验的中文复盘报告**：故障信息收集 → 时间线梳理 → 5Why 根因分析 → 改进项跟踪表 → 硬校验 → 定稿渲染。适用技术故障：线上服务事故、数据库故障、发布事故、网络中断等。

## 双模式路由

| 用户意图 | 模式 | 输出 |
|---|---|---|
| 刚出了一次故障，要写复盘报告 | `fupan` | 收集 → 时间线 → 5Why → 改进项 → 校验 → 中文报告 |
| 复盘方法、无责文化、报告写法等问题 | `guide` | 按 `references/fupan-method.md` 直接给答案 |

## fupan 模式流程

### 步骤 1：一次问清故障信息

先问清七项（用户没给的不许编）：
1. 故障现象（一句话：什么服务、什么表现）
2. 故障起止时间（发现时间、恢复时间，用北京时间注明）
3. 影响范围（多少用户/请求失败数/持续时间，数字没有就标"未核实"）
4. 故障等级（按团队自己的分级口径，没有就写"未定级"不许自创）
5. 关键事件点（告警、首次响应、止血动作、恢复确认，越具体越好）
6. 相关系统/服务（涉及哪些模块、中间件）
7. 材料来源（告警截图、监控曲线、聊天记录、口述——口述标"未核实"）

🔴 CHECKPOINT：把"故障现象 + 起止时间 + 影响范围"复述给用户确认后再往下走。用户没给的影响数字不许估算。

### 步骤 2：时间线梳理

- 按时间递增排列，一行一个事件：时间、发生了什么、证据来源（告警/日志/口述，未核实标出来）
- 事实与判断严格分区：时间线里只写事实，分析写进根因章节
- 算出两个关键间隔：**发现间隔**（影响开始 → 有人察觉）、**止血间隔**（察觉 → 影响结束）
- 反例：❌ "14:20 可能是因为发布导致"（判断混进时间线） ✅ "14:20 发布系统 v2.3.1 上线（发布记录）；14:35 错误率告警（监控，未核实阈值）"

### 步骤 3：5Why 根因分析

- 从故障现象出发连问 5 个"为什么"，每个答案必须能被证据支撑
- 至少列出 2 个促成因素（"为什么这个问题能发生"），不许只有一个"根本原因"
- **"人为失误/操作失误"永远不许当结论**：它是问题的起点——要追问"是什么让这个错误容易犯、难发现、扩散快"
- 反例：❌ "根本原因是运维小王敲错了命令" ✅ "配置变更缺少二次确认环节，且该字段无格式校验，错误配置 30 秒内全量生效"

### 步骤 4：改进项跟踪表

- 每条改进项四要素缺一不可：事项、**负责人**、**截止时间**、可验证的验收标准
- 改进项分三类：**防复发**（让它不再发生）、**早发现**（下次更快察觉）、**快止血**（下次更快恢复）
- 数量控制在 8 条以内，抓最有杠杆的；被砍掉的列"备选未采纳"并写一句话原因
- 反例：❌ "加强配置管理意识"（无法验证） ✅ "发布系统对 config 字段增加格式校验，恶意值测试用例通过视为完成，负责人：运维值班，截止：2026-10-15"

### 步骤 5：硬校验

把复盘 JSON 落盘后跑脚本：

```cmd
python scripts\fupan_check.py fupan.json
```

脚本硬校验：时间线必须按时间递增、每条改进项必须有负责人和截止时间、根因不许出现"人为失误/操作失误/粗心"等甩锅词。**校验失败 exit 1，先修 JSON 再渲染报告。**

### 步骤 6：渲染中文报告

校验通过后按 `references/report-template.md` 渲染中文复盘报告，一次性交付。

🛑 STOP：以下情形停下来，先确认再继续：
- 故障还在救火中、影响未结束——先止血，复盘等影响结束再做
- 用户要求把责任定到某个人身上——本 skill 只做无责复盘，不接
- 用户拿不出任何事实材料（全靠推测）——先收集材料，不硬写
- 用户要求编造影响数字"让报告好看点"——拒绝，缺失写"未核实"

## guide 模式

直接回答复盘方法问题：无责文化怎么做、5Why 怎么问、时间线怎么写、改进项验收标准怎么写、复盘会议怎么开。答案依据 `references/fupan-method.md`，不确定的写"未查到"不许编。

## 反例总览

- ❌ "这次事故的根本原因是测试小李没测出来" ✅ "测试用例缺失该场景的回归覆盖，且发布流水线无自动化回归门禁"
- ❌ "影响约 10 万用户"（用户没给数字） ✅ "影响用户数：未核实（待从监控平台确认）"
- ❌ "改进项：提高警惕" ✅ "改进项：告警阈值按 P99 延迟重设，灰度验证通过视为完成，负责人：SRE 值班，截止：2026-10-20"
- ❌ 故障还在处理中就开始写复盘结论 ✅ 先止血，复盘报告在影响结束后 48 小时内完成

## 铁律红线

1. **无责文化**：报告中不出现指向个人的归咎表述；人只以角色出现在响应动作里（"值班工程师 14:32 回滚"），错误归因于让错误发生的系统和流程。
2. **不编造事实**：用户没给的时间、数字、原因一律写"未核实"或"待确认"，不许估算填补；动态数字注明来源与检索日期，查不到写"未查到"。
3. **用户自述按未核实处理**：口述回忆在时间线里标注来源为"口述（未核实）"。
4. **不承诺效果**：不说"做了这些改进就不会再出故障"；改进项只写验收标准，不写效果保证。
5. **不推荐具体机构/品牌**：不推荐具体监控厂商、咨询公司；工具只说品类（如"APM 工具"）。
6. **不给真人/公司下定论**：不评价涉事人员能力，不给外部供应商下"不靠谱"定论。
7. **复盘不等追责**：本 skill 不输出绩效评价材料；用户要求写追责结论时 STOP。
8. **定稿后不可改写**：报告评审通过后只追加 dated 附录，不重写历史。

## 脚本与模板

- `scripts/fupan_check.py`：复盘 JSON 硬校验（时间线递增、改进项四要素、无甩锅词），用法见脚本头部。
- `references/fupan-method.md`：5Why 方法、无责文化、时间线写法、复盘会议主持清单。
- `references/report-template.md`：中文复盘报告模板。
