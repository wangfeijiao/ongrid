# 漏洞台账

> 依赖漏洞全流程跟踪表。每次扫描/复扫后更新主表状态；扫描历史每次扫描追加一行（方法见 `scripts/scan_deps.py`，`--json` 输出用于与台账对比）。

## 基本信息

| 项目 | 内容 |
|------|------|
| 项目路径 | （例：/path/to/project） |
| 生态 | （例：PyPI / npm / Go / Maven / crates.io / RubyGems / Packagist） |
| 上次扫描 | （例：2026-09-15） |
| 安全评级 | （例：🟢 A 级 / 🟡 B 级 / 🟠 C 级 / 🔴 D 级 / ⛔ 最高危） |
| 待修复 | （例：3 个） |
| 清零目标 | 待修复 = 0（所有行变「已修复/已移除」） |
| 清零进度 | （例：已修复 3 / 共 8；复扫确认） |
| 下次复扫 | （例：2026-09-22，和用户约定后写入） |

## 漏洞主表

| 依赖 | 版本 | CVE | 严重度 | EPSS | 批次 | 状态 | 最小修复版本 | 发现日期 | 修复日期 |
|------|------|-----|--------|------|------|------|--------------|----------|----------|
| （例：lodash） | （例：4.17.20） | （例：CVE-2021-23337） | 高危 | （例：0.2133） | 第1批 | 待修复 | （例：4.18.0） | 2026-09-15 | |
| | | | | | | | | | |

「状态」列取值：待修复 / 已修复 / 已移除 / 已忽略。
「严重度」列取值：恶意 / 高危 / 中危 / 低危 / 未知（与扫描报告一致）。
「EPSS」列填 0~1 的小数（如 0.0234），无数据留空。
「批次」列取值：第1批 / 第2批 / 第3批（与「清零路线图」的分批一致）。

## 清零路线图

> 目标：漏洞清零（「漏洞主表」所有行变「已修复/已移除」+ 复扫 🟢 A 级）。按 EPSS 分批；同一依赖的多个 CVE 合并成一次升级（升到覆盖所有 CVE 的最小修复版本）。

| 批次 | 动作（依赖 → 目标版本） | 覆盖 CVE | 修复命令 | 状态 | 完成日期 |
|------|------------------------|----------|----------|------|----------|
| 第1批（立即：🔴 正在被攻击 / ⛔ 恶意包） | （例：lodash → 4.18.0） | （例：CVE-2021-23337） | （例：npm install lodash@4.18.0） | 未开始 / 进行中 / 完成 | |
| 第2批（近期：🟠 较可能被利用 1%~10%） | | | | | |
| 第3批（长期：⚪ 理论风险 < 1%） | | | | | |

「批次」状态取值：未开始 / 进行中 / 完成。每完成一批，更新本表状态 + 完成日期，并同步「漏洞主表」对应行的「状态」「修复日期」，再复扫刷新「清零进度」。

## 使用说明

1. 每次扫描/复扫后，按扫描结果更新「漏洞主表」各行的「状态」；
2. 首次扫描后，AI 生成「清零路线图」写入本表，并给「漏洞主表」每行标注「批次」；
3. 每完成一批，把该批「状态」改为「完成」+ 填「完成日期」，同步更新「漏洞主表」对应行的「状态」「修复日期」，并复扫刷新「清零进度」；
4. 复扫时按 `(依赖, CVE)` 键与上次对比，再更新「扫描历史」和「清零进度」；
5. 每次对话结束前，与用户约定「下次复扫日期」并写入基本信息；
6. 状态为「已修复 / 已移除」的行保留在台账中（用于追踪历史，不要删行）。
