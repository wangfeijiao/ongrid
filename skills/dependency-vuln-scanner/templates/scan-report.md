# 依赖漏洞扫描报告模板

脚本 `scan_deps.py` 已输出完整报告（漏洞清单 + 优先级排序）。AI 在脚本报告基础上补充「深度解读」时，按以下结构组织（语言与用户输入一致）。

```
# 依赖漏洞扫描报告

## 扫描概览
- 项目：【文件路径】
- 生态：【PyPI / npm / Go / Maven / crates.io / RubyGems / Packagist】
- 依赖数：【N 个，含/不含传递依赖】
- 漏洞数：【M 个】

## 漏洞清单（脚本已按严重度排序）
对每条漏洞：
- 依赖与版本：【如 lodash 4.17.20】
- 漏洞编号与说明：【CVE-2021-23337 — 命令注入】
- 严重度：【恶意 / 高危 / 中危 / 低危】
- 在野利用概率：【EPSS 百分比，如 21.3%】
- 修复版本：【最小修复版本，如 4.17.21】
- 修复命令：【npm install lodash@4.17.21】

## 优先级排序（先修哪些）
- ⛔ 恶意包（N 个）：立即移除，不要升级
- 🔴 正在被攻击（EPSS ≥ 10%，N 个）：优先处理
- 🟠 较可能被利用（EPSS 1%~10%，N 个）：纳入近期计划
- ⚪ 理论风险（EPSS < 1%，N 个）：可纳入长期计划

## 深度解读（AI 补充，脚本给不了的部分）
- 影响评估：结合用户使用场景，说明每个高危漏洞实际风险多大
- 升级建议：多个 CVE 修复版本不一致时，建议升到覆盖所有漏洞的最高版本；大版本跨越的破坏性变更风险
- 替代方案：某库已停维护 / 无修复版本时，推荐替代库

## 下一步
- 改完依赖后重新扫描，确认漏洞清零
```

## 报告注意事项

- **不替用户下结论**：说「此漏洞高危（EPSS 95%），修复于 X，升级成本取决于你的项目」，而非「你应该立即升级」；
- **区分事实与判断**：脚本输出的严重度、EPSS、修复版本是客观事实；「建议先修哪个」是基于事实的排序，不是替用户拍板；
- **EPSS 是群体统计**：EPSS 0.1% 是「所有暴露该系统未来 30 天被攻击的比例」，高价值目标（银行/大厂）实际风险更高，务必提醒；
- **传递依赖是可选加餐**：用户只给直接依赖清单时，先给完整报告，再主动问「要不要查传递依赖」，不要因没锁文件就说「扫描不完整」。
