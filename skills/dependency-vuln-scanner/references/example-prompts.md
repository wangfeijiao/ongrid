# 对话示例（怎么用这个技能）

> 四个典型场景，展示技能如何回应。语言与用户输入一致。

---

## 场景一：首次扫描（提供 package.json）

**用户：**
这是我的 package.json，帮我看看有没有漏洞。

**助手：**
收到，先确认文件内容——

```json
{
  "dependencies": {
    "express": "^4.17.1",
    "lodash": "^4.17.19",
    "axios": "^0.21.1"
  }
}
```

运行扫描脚本：

```
python3 scripts/scan_deps.py /path/to/package.json
```

扫描结果：**3 个依赖中有 2 个存在已知漏洞，共 3 个 CVE**。安全评级：🔴 D 级（存在高危漏洞）。

| 依赖 | CVE | 严重度 | EPSS | 最小修复版本 |
|---|---|---|---|---|
| lodash 4.17.19 | CVE-2021-23337 | 高危 | 21.3% 🔴 | 4.17.21 |
| lodash 4.17.19 | CVE-2020-28500 | 中危 | 7.3% 🟠 | 4.17.21 |
| axios 0.21.1 | CVE-2021-3749 | 高危 | 1.6% 🟠 | 0.21.2 |

**优先级排序**（按 EPSS 降序，同一依赖合并）：
- 🔴 **第 1 批·立即修**：lodash（含 CVE-2021-23337，EPSS 21.3%，正在被攻击）→ 一次升到 4.17.21，同时覆盖它另一个 CVE
- 🟠 **第 2 批·近期修**：axios（EPSS 1.6%，较可能被利用）
- 🟢 **第 3 批·长期**：本次无

---

先说两个术语——**CVE** 是漏洞的编号，像身份证号，每个公开漏洞都有唯一编号；**EPSS** 是公开数据源，估算「这个漏洞未来 30 天被攻击的概率」——CVSS 告诉你「危害多大」，EPSS 告诉你「是不是正在被攻击」。

lodash 的 CVE-2021-23337 EPSS 21.3%，属于**正在被攻击**的区间，不是理论风险；axios 的 EPSS 1.6%，属于「较可能被利用」但还没到红区。

---

### 清零路线图

**目标状态**：漏洞主表全部「已修复」 + 复扫 🟢 A 级 = 清零。

**第 1 批（立即）**：升 lodash → 修掉 2 个 🔴 漏洞

```bash
npm install lodash@4.17.21
```

→ 改完跑 `python3 scripts/scan_deps.py package.json`，确认 lodash 两项消失。

**第 2 批（近期）**：升 axios → 修掉 1 个 🟠 漏洞

```bash
npm install axios@0.21.2
```

→ 改完复扫，确认 axios 清零。

**全部完成后**：你的依赖在 OSV.dev 收录范围内就是干净的。🟢 A 级。

---

另外，你这次给的是 package.json（直接依赖清单）。要不要我帮你查更深一层的传递依赖（依赖的依赖的漏洞）？如果有 package-lock.json，发我就行。

我现在帮你建 `漏洞台账.md`，记下这次基线，下次复扫直接对比。下次复扫建议在 **2 周后（2026-09-29）**，改完依赖就回来，我帮你确认清零。

## 场景三：无漏洞（保持干净）

**用户：**
扫一下我的依赖。

**助手：**
确认文件——requirements.txt：

```
flask==3.0.0
requests==2.31.0
pydantic==2.5.0
```

运行扫描：

```
python3 scripts/scan_deps.py /path/to/requirements.txt
```

扫描结果：**未发现已知漏洞**。安全评级：🟢 A 级。

---

### 🟢 A 级边界说明

A 级 = 在 OSV.dev 收录范围内干净，**不等于零风险**。0-day（刚被发现、还没公开的漏洞）未入库，任何对照漏洞库的扫描工具——包括 Snyk、GitHub Dependabot——都查不出。但真正威胁开发者的，绝大多数是「已知但没打补丁的漏洞」，这正是本技能帮你能发现的。

### 保持干净的 4 个建议

1. **接入 CI**：用 `python3 scripts/scan_deps.py requirements.txt --sarif` 输出 SARIF 格式，接到 GitHub Code Scanning，每次提交自动查；
2. **定期复扫**：漏洞库每天更新，建议 **每月复扫一次**；
3. **用锁文件**：如果有 poetry.lock 或 Pipfile.lock，固定传递依赖版本，避免依赖漂移引入新漏洞；
4. **减少依赖面**：定期审视依赖清单，淘汰停维护的库。

---

虽然这次没漏洞，我帮你建 `漏洞台账.md` 记录基线——否则下次复扫无从对比。下次复扫建议 **2026-10-15**，到点回来，保持干净就是一次有回访价值的交付。

要不要我帮你查传递依赖？如果有 poetry.lock 或 Pipfile.lock，发我就行。

别分批了，我想一次全修完。

**助手：**
完全可以。分批只是 EPSS 优先级建议——能一次修完就一次修完，不存在必须等待。

下面是完整的一次性修复命令清单（按你台账里全部待修复漏洞）：

```bash
# 第 1 批（EPSS ≥ 10%，正在被攻击）
npm install lodash@4.17.21

# 第 2 批（EPSS 1%~10%，较可能被利用）
```

一次全跑完：

```bash

```

然后复扫验证：

```
python3 scripts/scan_deps.py /path/to/package.json --json
```

确认结果：全部 3 个 CVE 消失，🟢 A 级，清零完成。
