# 严重度分级与 EPSS 优先级定义

深度解读报告时，对照本指南，确保严重度与优先级分级准确、不拔高不淡化。

## 1. 安全评级（整体项目）

| 评级 | 条件 | 含义 |
|------|------|------|
| ⛔ 最高危 | 发现恶意包（MAL- 前缀） | 供应链投毒，比任何 CVE 都紧急 |
| 🟢 A 级 | 未发现已知漏洞 | 在 OSV.dev 收录范围内干净 |
| 🔴 D 级 | 存在高危漏洞 | 有 CVSS 高危，需尽快处理 |
| 🟠 C 级 | 存在中危漏洞 | 有中危，纳入升级计划 |
| 🟡 B 级 | 仅低危漏洞 | 低风险，可缓 |

## 2. 单条漏洞严重度（CVSS）

| 级别 | 判定依据 |
|------|----------|
| 恶意 | 漏洞 ID 以 `MAL-` 开头，或 summary 明确说「malicious package / malicious code」 |
| 高危 | CVSS 机密性+完整性均为 High（C:H + I:H），或分数 ≥ 9.0 |
| 中危 | 机密性/完整性/可用性任一 High，或分数 ≥ 7.0 |
| 低危 | 其余有 CVSS 记录的漏洞 |
| 未知 | 无 CVSS 数据 |

**关键区分**：CVSS 衡量「如果被利用，危害多大」，是漏洞的固有属性。

## 3. EPSS 优先级分层（在野利用概率）

EPSS（Exploit Prediction Scoring System，FIRST.org）衡量「该漏洞未来 30 天被实际利用的概率」，是**真实世界攻击数据**，与 CVSS 正交。

| 分层 | EPSS 范围 | 标签 | 处理建议 |
|------|-----------|------|----------|
| 🔴 正在被攻击 | ≥ 10% | 在野利用 X% | 优先处理 |
| 🟠 较可能被利用 | 1% ~ 10% | 在野利用 X% | 纳入近期计划 |
| ⚪ 理论风险 | < 1% | 在野利用 X% | 可纳入长期计划 |
| ❓ 无数据 | 无 EPSS 记录 | 新披露漏洞 | 暂无利用数据，留意后续更新 |

## 4. 为什么「先修哪个」要看 EPSS 而非只看 CVSS

- **CVSS 高 ≠ 正在被攻击**：一个「高危」CVE 若太难利用，EPSS 可能 < 1%（现实中没人攻击）；
- **EPSS 高才意味着真实威胁**：Log4j（CVE-2021-44228）EPSS ≈ 99.999%，是「正在被大规模攻击」的典型；
- **正确顺序**：高 CVSS + 高 EPSS 优先修；低 CVSS + 低 EPSS 可缓。

## 5. 解读时的诚实边界

- **EPSS 是群体统计，不是针对你的预测**：EPSS 0.1% 是「所有暴露该漏洞的系统未来 30 天被攻击的比例」。高价值目标（银行、大厂）实际被攻击概率高于均值；
- **新 CVE 有时滞**：刚披露的 CVE 无历史数据，EPSS 可能不准；
- **EPSS 不替代决策**：EPSS 用于「优先级排序」的客观参考，不替代「该不该修」的决策（那取决于升级成本、业务场景、团队资源）。

## 6. 最小修复版本（避免破坏性变更）

- 脚本推荐「升级到恰好修复该 CVE 的最小版本」：如 lodash 4.17.20 的命令注入 CVE 修复于 4.17.21，就推荐 4.17.21，而非 latest 4.18.1（可能含破坏性变更）；
- 只有查不到 fixed 版本时才推荐「升级到最新版」；
- 多个 CVE 的修复版本不一致时，AI 应补充建议「升到覆盖所有漏洞的最高版本」。
