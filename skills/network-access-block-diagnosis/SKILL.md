# 网站打不开的分层排查法

> 一句话：**先分层，再定性。别在没确认是哪一层出问题时，就去换浏览器、清缓存。**

## 何时启用

- 「某个网页打不开 / 登录不了 / 一直转圈」
- 「换了网络还是不行」「手机热点也不行」
- 「是不是网站挂了」「是浏览器的问题吗」
- 任何访问失败、且用户已经尝试过重启/清缓存等无效动作的场景

## 第一步：决策树——先分清是哪类故障

拿到"打不开"的报告，**先问一句：是所有网站都打不开，还是只有这一个？**
这一个问题就能把排查范围砍掉一大半。

```
【入口】网站打不开
    │
    ├─ 目标是本机地址（127.0.0.1 / localhost）？
    │      │
    │      └─ 是 → 【D 本机服务】先绕过代理直连一次（见纪律五）
    │            代理会把回环请求也劫走，表现为 502 / 连不上，
    │            而服务其实健康。别去重启服务、翻日志。
    │            终止条件：直连探测出真实状态码
    │
    ├─ 全部网站都不行？
    │      │
    │      ├─ 是 → 【A 全局故障】问题在本机网络
    │      │     动作：查 Wi-Fi/网线 → 重启光猫 → nslookup 任意域名
    │      │     终止条件：任意网站恢复访问
    │      │     ※ 不需要跑本技能的探测脚本，直接修网络
    │      │
    │      └─ 只有这一个网站不行 → 走 B 或 C
    │
    ├─【B 单个站点挂】其他网站正常，就它不行
    │      │
    │      └─ 动作：跑诊断脚本（见下）→ 按状态码定性
    │            ├─ 429/403/451 + 拦截页 → WAF 层，换网/等待/申诉
    │            ├─ 401 → 通路正常，去重新登录（别查网络）
    │            ├─ 连不上(0) → DNS/防火墙，走本机排查
    │            └─ 4xx/5xx 业务码 → 请求已到后端，看业务侧
    │      终止条件：脚本结论为「正常可访问」且 --confirm 通过
    │
    └─【C 仅浏览器挂】脚本探测正常(200)，但浏览器里就是打不开
           │
           └─ 问题锁定在浏览器层，动作按序：
                 1. 无痕模式打开（排除扩展/Cookie）
                 2. 换一个浏览器内核（Chrome↔Edge↔Firefox）
                 3. 清该站点 Cookie 与缓存
                 4. 关代理/VPN 插件
           终止条件：任一浏览器能正常打开
```

**用 --browser 参数可以自动化 C 类的验证**：脚本会用真实浏览器渲染页面并截图，
直接看到"是拦截页还是正常页面"，不用人工换浏览器试。

## 核心：四层判据模型

从外到内逐层排除，**每层都要能被证伪**，不要跳过。

| 层 | 检查什么 | 怎么查 | 若是这层的问题 |
|---|---|---|---|
| ① 浏览器 | 是否浏览器特有 | `--browser` 实测截图 / 换浏览器无痕 | 清缓存、重置设置、换浏览器 |
| ② 本机网络 | DNS 与 TLS 是否通 | `nslookup` + `curl -v` 看握手 | 改 DNS、查防火墙 |
| ③ 出口 IP | 公网 IP 是否被服务端标记 | 查出口 IP + 对比换网后是否变化 | 换网、等待限流解除 |
| ④ 服务端 WAF | 是否返回拦截页 | 看响应码与响应体 | 申诉、等待、换网络 |

**关键判据：看返回的是「业务响应」还是「拦截页」。**
- 返回业务 JSON / 正常 HTML → 请求已到达后端，①②③ 层都通，问题在业务侧或账号侧
- 返回 `429 / 403` + 一张 WAF 拦截页（如华为云 "Request Blocked"、Cloudflare "Ray ID"）→ **请求在 WAF 层就被拒，压根没到后端**。这时换浏览器、清缓存、换账号 100% 无效，因为拦截依据是出口 IP

## 四条反直觉纪律（都是实战踩坑换来的）

### 纪律一：换网是否生效，只认出口公网 IP

**不能相信「我连了热点」这个描述。** 实战踩坑：用户开热点后说"热点也不行"，
但检测发现默认路由仍是原网网关、出口 IP 一个字符都没变 —— 热点压根没生效
（多为信号弱被自动切回原 Wi-Fi，或手动切换没成功）。

→ **动作**：任何"换网后仍不行"的结论，必须先核对出口公网 IP 是否真的变了。
IP 没变 = 这次换网没生效，结论作废，重来。

```
route print 0.0.0.0        # 看默认路由指向哪个网关
curl -s https://myip.ipip.net   # 看出口公网 IP 与归属地
```

### 纪律二：检测必须绕开本机注入的代理

AI 工具会话（本机跑的各类 agent）常会**动态开一个本地代理端口**并注入到工具进程的环境变量里。
如果不绕开，请求会走这个代理，可能得到 `502 Bad Gateway` 之类的假故障，
**把「代理不通」误判成「目标站不通」**。

→ **动作**：检测时强制直连。
```
curl --noproxy '*' https://目标站/
```
脚本里用 `urllib.request.ProxyHandler({})` 实现同样的效果。

> 注意：该代理通常**不是系统代理**（`netsh winhttp show proxy` 显示"直接访问"），
> 只存在于工具进程的环境变量中，所以浏览器不受影响 —— 别把它当成浏览器的代理来查。

### 纪律三：浏览器判定只认拦截页标题，不拿宽泛词扫正文

实战踩坑：给浏览器实测加"验证码"关键词判定，结果 DeepSeek 登录页被误判成
"人机验证"——因为页面正文里有"发送验证码"按钮。

→ **动作**：
- WAF 拦截页的**标题**高度特征化（"Request Blocked"、"Just a Moment"、"Attention Required"），只认标题
- 正文关键词只在该页面**几乎无内容**（<400 字符）时才作数——拦截页正文短，业务页长
- 拿不准就**看截图**，脚本每次实测都存图

### 纪律四：判定"恢复"要连测多次，单次通过不算数

限流解除的边界处常有波动：第一请求通了，第二个又被拦。
单次 200 就宣布恢复，会得到"时好时坏"的困惑结论。

→ **动作**：用 `--confirm` 模式，连测 3 次（间隔 5 秒）全部 200 才判定稳定恢复。
持续监测模式（`--watch`）里已内置此逻辑。

### 纪律五：目标是本机地址时，代理是头号嫌疑人

前四条都默认目标在公网上。**目标换成 `127.0.0.1:<port>` / `localhost` 时，
纪律二会以最反直觉的方式复现：回环请求同样会被代理劫走。**

实测：本机服务在 `127.0.0.1:8799` 正常监听，`netstat` 显示 LISTENING、
直接 socket 探测返回 `HTTP 200`；但同一时刻 `curl 127.0.0.1:8799` 返回
`502 Bad Gateway`。**服务是健康的，是代理把请求吞了。**

为害之处在于 `502` 直觉上读作"服务挂了"，于是去重启服务、查端口、翻日志——
全都白费，因为问题根本不在服务侧。而服务日志往往是干净的，
这会进一步把人往"服务根本没起来"的方向带偏。

→ **动作**：判定顺序固定为「先绕过代理直连一次，再谈服务是否健康」。

```bash
# 错误：可能被代理拦截，得到 502 假故障
curl http://127.0.0.1:8799/api/health

# 正确：强制直连
curl --noproxy '*' http://127.0.0.1:8799/api/health
```

> **两个必须知道的细节**
>
> 1. `--noproxy` 只影响 curl 自己。脚本里要**同时**做两件事：
>    从环境里 `pop` 掉 `HTTP_PROXY` / `HTTPS_PROXY`（**含小写形式**，
>    小写变量同样会被识别）并设 `NO_PROXY=*`。只设 `NO_PROXY`
>    在部分客户端上不生效。
> 2. 浏览器**不受影响**——该代理只存在于工具进程的环境变量里，
>    不是系统代理（`netsh winhttp show proxy` 会显示"直接访问"）。
>    所以「浏览器能打开、命令行打不开」正是本情况的典型指纹。

**判定指纹（三条同时出现即可定性）**

| 观察 | 结果 |
|---|---|
| `netstat -ano \| findstr <端口> \| findstr LISTENING` | 有输出（服务在听） |
| 绕过代理直连 | `200` |
| 不绕过代理 | `502` 或连接失败 |

## 状态码人话对照表

| 状态码 | 人话 | 归属层 | 该怎么办 |
|---|---|---|---|
| 200 | 正常 | app | — |
| 301/302/307/308 | 跳转 | app | 站点存活，改访问地址 |
| 400 | 请求格式错 | app | 检查参数 |
| **401** | 未认证 | app | **通路正常**，重新登录/换 Token，**别去查网络** |
| **403** | 被拒绝 | waf | WAF 封禁或需登录态，换合法网络 |
| 404 | 不存在 | app | 站点通，路径写错了 |
| 405 | 方法不允许 | app | **接口正常**，探测用了 GET（改 POST） |
| 407 | 需代理认证 | browser | 检查代理客户端认证配置 |
| 408 | 请求超时 | local | 查本机上行链路 |
| **422** | 参数校验失败 | app | **请求已达业务后端 → 通路正常**（强证据） |
| **429** | 被限流 | egress | **出口 IP 被标记**，换网（核对IP变了没）或等解除 |
| **451** | 法律原因不可用 | waf | 地域封锁，换网络通常无效 |
| 500 | 服务端错误 | server | 等服务端恢复 |
| 502 | 网关异常 | browser | **优先怀疑本机代理**，其次服务端。目标是回环地址时几乎必是本机代理（纪律五） |
| 503/504 | 不可用/超时 | server | 等数分钟重试 |
| 521 | 源站不可达 | server | Cloudflare 连不上源站，等 |
| 525 | SSL 握手失败 | server | 服务端证书问题，等 |
| 连不上(0) | 网络不通 | local | 查 DNS / 防火墙 / 物理链路 |

**三个最容易误判的点**：
- `405` 和 `422` 都说明**通路是好的**，是探测方法不当造成的假故障。探测登录类接口务必用 **POST**
- `502` 在 AI 工具会话里**优先怀疑本机代理**（纪律二），别急着怪服务端
- `401` 是业务问题不是网络问题，别顺着"打不开"就往网络方向查

## 排查工序

0. **先看目标是不是本机地址**（`127.0.0.1` / `localhost`）。
   是就先绕过代理直连一次——这一步不花钱，却能省掉后面所有无效排查（纪律五）
1. **问清现象**：全部站点挂还是单个站点挂？（决策树入口）
2. **跑检测脚本**：`python scripts/site_check.py --site <域名>`，一次拿到出口 IP + 路由 + 状态码
3. **需要浏览器证据时**：加 `--browser`，拿真实渲染截图定性
4. **若要换网验证**：换完**先看出口 IP 变没变**，再跑一次脚本
5. **若确认是 WAF 限流**：提取追踪 ID → 建议换网或静置数小时 → 提示勿反复刷新（会加重标记）
6. **宣布恢复前**：用 `--confirm` 连测 3 次全过，才算稳定恢复

## 随附脚本

`scripts/site_check.py` —— 通用站点诊断脚本（默认探测 deepseek，可换任意站点）

```bash
# 单次诊断（HTTP 探测）
python site_check.py --site chat.deepseek.com --urls / --urls /api/v0/users/login

# 加浏览器实测：真实渲染 + 截图，自动识别拦截页/人机验证/正常页
python site_check.py --site chat.deepseek.com --browser --shots shots/

# JSON 输出（供自动化/其他工具消费），并追加到 JSONL 历史日志
python site_check.py --site example.com --json --log history.jsonl

# 本机服务的真实状态（脚本内部已强制绕过代理；回环地址自动按 http 探测）
python site_check.py --site 127.0.0.1:8799 --urls /api/health

# 恢复确认：连测 3 次全过才宣布稳定
python site_check.py --site example.com --confirm

# 持续监测，恢复（含确认）后自动停止；每 10 分钟一次
python site_check.py --site example.com --watch 10 --confirm --log history.jsonl

# 退出码：0=正常，2=异常（可直接接入 shell 判断/定时任务告警）
```

**输出内容**：出口公网 IP 与归属地、默认路由、各路径状态码与耗时、
归属层判定与建议动作、被拦截时的 WAF 追踪 ID、浏览器实测截图路径、
可选的 JSON 结构化结果与 JSONL 历史。

**浏览器实测的实现要点**（改环境时需注意）：
- 用 `playwright-core`（Node）驱动本机已缓存的 chromium，无需额外安装
- **必须显式传 `executablePath`**：playwright 版本号与浏览器缓存版本号经常不一致
  （实战踩坑：playwright 期待 1243，本机缓存只有 1228，不传路径直接报错）
- 脚本会**自动扫描** node 版本目录与 `%LOCALAPPDATA%\ms-playwright`，各取最高可用版本，
  不写死版本号（目录名会随安装变动）

**可配置项**（环境变量，均有自动探测兜底，通常无需设置）：

| 变量 | 作用 | 默认 |
|---|---|---|
| `SITE_CHECK_NODE` | 指定 node 可执行文件 | 自动扫描 node 版本目录，退到 PATH |
| `SITE_CHECK_CHROME` | 指定 chromium 可执行文件 | 自动扫描 ms-playwright 缓存 |
| `SITE_CHECK_NODE_MODULES` | `playwright-core` 所在 node_modules | 托管工作区目录 |

> Windows / Git Bash 注意：以 `/` 开头的参数可能被 MSYS 转成本地路径。
> 加 `MSYS_NO_PATHCONV=1` 前缀可规避（脚本内也做了兜底还原）。

## 边界

- **不判断服务是否"应该"可用**，只判断当前链路能否打通。
- **不做任何形式的绕过**（不提供改 IP、代理池、破解封禁的方案）。限流的正当处理是换合法网络或等待。
- 若所有站点都打不开，问题在本机网络，直接走决策树 A 分支，无需跑脚本。
- 浏览器实测依赖本机有 playwright-core + chromium 缓存；没有时脚本会明确报错并降级为纯 HTTP 探测，不会中断诊断。
