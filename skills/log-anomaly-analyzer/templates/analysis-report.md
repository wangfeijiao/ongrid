# 日志异常排查报告模板

生成报告时按以下结构输出（输出时去掉代码块标记，直接输出标题与正文）。语言与用户输入一致。

```
# 日志异常排查报告

## 分析概览
- 日志文件：【路径 / 粘贴内容】
- 总行数：【N】
- 时间范围：【起 ~ 止】
- 错误占比：【X%（错误 N 条）】
- 识别领域：【Nginx / Kubernetes / MySQL / 通用】（按 SKILL.md 第三步的领域识别规则判断）
- 整体判断：✅ 健康 / ⚠️ 有异常 / 🔴 严重异常

## 高频异常模式（按频次排序）
对每个 TOP 模式：
- 模式：【掩码后的模板】
- 频次：【N 次（X%）】
- 样例：【一条真实样例】
- 类型：【属于哪类错误（对照 error-catalog 或对应领域知识）】
- 根因推断：【最可能的根因，标注是推断】
- 修复方案：【具体可执行的修复动作，改了哪里、怎么改】

## 因果链归并
把时间上先后出现、语义相关的模式归并为根因链：
- 【根因链 1】`模式A` → `模式B` → 同一根因【...】，影响【N 条日志】
- 【根因链 2】...

## 时间线分析
- 【脚本检测到的突增/分布情况】
- 【判断：突发故障 / 慢性问题 / 周期性，及依据】

## 异常类型与来源
- 异常类型 TOP：【...】
- 高频错误接口/状态码/IP：【...】
- 影响范围判断：【...】

## 排查结论与建议
1. 【最优先处理的问题 + 修复方案】
2. 【次要问题 + 修复方案】
3. 【长期建议】
```

## 报告注意事项

- **事实与推断分离**：脚本统计的「频次、占比、时间分布」是事实；「根因」是推断，必须明确标注；
- **优先级**：频次高 × 影响大 的异常排最前，不要按日志出现顺序罗列；
- **归并同根因**：`connection refused` 和 `retry failed` 这类同一条链上的模式，归并说明，不要在「高频模式」里重复展开；
- **修复方案要可执行**：如「调大 `max_connections` 到 500」「给 orders 表 id 字段加索引」，而非空泛的「检查一下」；
- **过滤噪音**：健康检查、探活等正常日志不要出现在异常模式里（对照领域知识的「噪音日志」章节）。
