# 性能自适应策略

> 清理是典型的**重 IO + 高内存**任务，很容易把用户正在用的电脑拖垮。
> **本文件的第一原则：只有在机器存在性能冗余时，才允许开始清理。没有冗余就不做，或者先降档。**
> 本文件规定：执行前必须先做性能画像并计算冗余度，再据此决定扫描深度、批次大小与让步频率；
> 执行中还要持续复查冗余，掉下来就自动降档或中止。
>
> 真实教训：16 GB 内存的机器上，用 `Get-ChildItem -Recurse` 扫 1.7 万个文件的目录，
> 配合浏览器与若干 AI 工具同时开启，直接导致整机卡死强制重启。

---

## 零、冗余度：本技能的第一决策依据

**核心原则：清理不能吃掉机器的余量。** 判断标准不是"内存还剩多少"，
而是"**清理操作自己会占用多少，做完之后还能剩多少**"。

### 冗余度定义

```
冗余度 = 清理前的可用内存 − 清理过程的预估峰值占用
```

清理过程的预估峰值占用，取下列三者之和：

| 组成 | 估算方法 |
|---|---|
| 脚本自身内存 | 流式枚举模式约 **50–200 MB**（若误用整树读入，可达 1 GB+） |
| 文件系统缓存 | 遍历的文件元数据量，经验值 **100–400 MB** |
| 用户已有负载的波动 | 浏览器/AI 工具等前台程序在清理期间的自然增长，取 **500 MB–1.5 GB** |

### 冗余等级与动作

| 冗余度 | 等级 | 动作 |
|---|---|---|
| **> 4 GB** | 充裕 | 可开 `-Deep` 深度扫描，单批 ≤ 10 项 |
| **2–4 GB** | 足够 | 只扫已知目标清单，单批 ≤ 5 项 |
| **1–2 GB** | 紧张 | **降档执行**：单批 ≤ 3 项，让步频率翻倍；并向用户说明"当前余量偏紧，我会放慢" |
| **< 1 GB** | **不足** | **拒绝开始清理**。只做浅层只读扫描，明确告知用户：需先关闭若干程序释放内存，或稍后再来 |

**这一条是硬门槛。** 冗余不足时用户若坚持要清理，必须说明风险（可能卡死）并要求二次确认，
但仍要在报告中建议延后。

### 冗余不足时的标准处置话术

> 当前可用内存 X GB，清理过程预计需要 Y GB 余量。**现在开始有可能导致电脑卡顿甚至卡死。**
> 建议先关闭以下程序再继续：<列出占用内存最高的几个进程>。
> 或者我先只做只读扫描（几乎不占资源），把要清理的清单列出来，你等方便的时候再执行。

## 一、执行前必做的性能画像

```powershell
$cpu = Get-CimInstance Win32_Processor | Select-Object -First 1
$os  = Get-CimInstance Win32_OperatingSystem
$memFreeGB = $os.FreePhysicalMemory / 1MB
$memTotalGB = $os.TotalVisibleMemorySize / 1MB
$cpuLoad = (Get-CimInstance Win32_Processor | Measure-Object -Property LoadPercentage -Average).Average
Get-PhysicalDisk | Select-Object FriendlyName, MediaType, BusType, Size
```

采集四项：**可用内存、CPU 负载、磁盘介质（HDD/SSD/NVMe）、磁盘总线**。

### 同时必须采集"用户当前负载基线"

清理会与用户正在运行的程序争抢资源，所以要知道用户此刻在跑什么：

```powershell
# 按内存占用排序的前 8 个进程，用于判断用户当前负载
Get-Process | Sort-Object WorkingSet64 -Descending |
  Select-Object -First 8 Name,
    @{N='MemMB';E={[math]::Round($_.WorkingSet64/1MB,0)}}
```

若发现浏览器（多标签）、IDE、虚拟机、大型 AI 客户端等重负载程序在跑，
在报告中标注"当前检测到 X 个重负载程序，会挤占余量"。
**若冗余度落在"紧张"或"不足"档，建议用户先关掉其中不用的。**

## 二、节奏分级表

综合冗余度与磁盘类型决定执行节奏：

| 档次 | 触发条件 | 批次上限 | 让步频率 | 扫描深度 |
|---|---|---|---|---|
| **正常 NORMAL** | 冗余 > 4 GB | 每批 ≤ 10 项 | 每 3000–4000 文件让出 120 ms | 可开 `-Deep` |
| **保守 CONSERVATIVE** | 冗余 2–4 GB | 每批 ≤ 5 项 | 每 2000 文件让出 200 ms | 只扫已知目标清单 |
| **紧张 TIGHT** | 冗余 1–2 GB | 每批 ≤ 3 项 | 每 1500 文件让出 300 ms | 只扫已知目标清单 |
| **不足 INSUFFICIENT** | 冗余 < 1 GB | **不执行删除** | — | 仅浅层扫描并建议延后 |
| **延后 DEFER** | CPU 负载 > 70% | 不启动 | — | 直接向用户报告"当前负载高，建议稍后" |

**内存是真瓶颈，磁盘通常不是。** 除非检测到 `MediaType = HDD`，那时让步频率再提高一档
（每 1000 文件让出 300 ms），因为机械盘的随机寻道会成为主要瓶颈。

## 三、执行中的动态冗余复查（不可跳过）

机器负载是**动态变化**的 —— 用户随时可能新开程序。因此每批结束时必须重新采样一次冗余度：

```powershell
# 每批结束、清空回收站之后执行
$memFreeGB = (Get-CimInstance Win32_OperatingSystem).FreePhysicalMemory / 1MB
$cpuLoad   = (Get-CimInstance Win32_Processor | Measure-Object -Property LoadPercentage -Average).Average
```

**降档规则**（自动执行，不必询问用户，但要在日志与报告中记录）：

| 复查结果 | 动作 |
|---|---|
| 冗余跌破原档次下限 | **自动降一档**（批次上限减半、让步频率翻倍），下一批生效 |
| 冗余跌破 1 GB | **立即中止后续批次**，已完成的保留，如实报告剩余项 |
| CPU 负载持续 > 70% | 批次间停顿从 2 秒延长到 5 秒 |
| 用户主动反馈"卡了" | **立即中止**，不等待本批完成 |

降档与中止都必须让用户知情。中止时的标准措辞：

> 检测到可用内存已降至 X GB，为保证电脑不卡，我停在了第 N 项。
> 已释放 Y GB。剩余 Z 项未处理，等你方便时我再继续。

## 四、必须遵守的五条铁律

1. **单任务串行。** 任何时候只允许一个扫描或清理任务在跑。禁止并行开多个任务——这是上次卡死的直接原因之一。

2. **进程自我降级。** 每个 PowerShell 脚本开头执行：
   ```powershell
   try { (Get-Process -Id $PID).PriorityClass = 'Idle' } catch {}
   ```
   让用户的交互操作永远抢占资源。

3. **流式枚举，绝不整树读入内存。**
   ```powershell
   # 禁止
   $files = Get-ChildItem -Path $p -Recurse -File -Force
   $size  = ($files | Measure-Object -Property Length -Sum).Sum

   # 必须
   $sum = 0; $cnt = 0
   foreach ($f in [System.IO.Directory]::EnumerateFiles($p,'*',[System.IO.SearchOption]::AllDirectories)) {
       try { $sum += ([System.IO.FileInfo]::new($f)).Length; $cnt++ } catch {}
       if ($cnt % 3000 -eq 0) { Start-Sleep -Milliseconds 120 }
   }
   ```
   同一工作量：从**数分钟且卡死** → **十几秒流畅**。

4. **每个目录只扫一遍。** 不要"删前扫一次、删后扫一次"。改为：删除前用文件系统已有的体积数据（来自扫描报告），删除后用整盘可用空间差值来验证。

5. **每批之间留缓冲。** 批次间 `Start-Sleep -Seconds 2`（CPU 高负载时 5 秒），让文件缓存与磁盘队列排空。

## 五、进度反馈规范

长任务（> 20 秒）必须让用户知道在做什么，否则用户会以为程序卡死而强制结束：

- 每处理 N 个目录输出一行进度到结果文件
- 报告中使用"当前正在处理：<项目名>（第 x/y 项）"的措辞
- 单个项目耗时超过 30 秒时，说明原因（如"npm 缓存含 1.7 万个文件，逐个删除较慢"）

## 六、什么时候该停下来

出现下列任一情况，**立即停止后续批次并报告用户**：

- **冗余度跌破 1 GB**（首要触发条件）
- 可用内存绝对跌破 3 GB
- 出现明显的系统无响应（命令超时、磁盘队列持续 100%）
- CPU 负载持续 > 70%
- 单批执行时间超过预估的 3 倍
- 用户主动反馈"卡了"

停止时要如实说明：已完成到哪一项、释放了多少、剩余哪些未做。**宁可少做一批，不要硬撑。**

## 七、macOS / Linux 等价采集命令

```bash
# 可用内存（macOS）
vm_stat | awk '/free/{print $3*4096/1024/1024" MB"}'

# 可用内存（Linux）
free -m | awk '/Mem:/{print $7" MB available"}'

# CPU 负载
uptime

# 重负载进程 TOP 8
ps aux --sort=-%mem | head -9

# 磁盘类型（判断是否 HDD）
diskutil info / | grep "Solid State"     # macOS
lsblk -d -o NAME,ROTA                    # Linux（ROTA=1 为机械盘）
```
