# 复盘模板与归因方法

> 四部分：六段式模板 + 5Why归因方法（含停止标准）+ 改进项分级 + 故障等级参照。

## 一、六段式复盘文档模板

### 段1：故障摘要（3句话以内）
写什么：什么故障、影响多大、当前状态。
口径示例：「2026-03-14 21:15-22:05，优惠券表被定时任务锁定，领券接口失败50分钟，影响用户约X万。根因为未登记的定时任务在高峰期持锁。当前已恢复，任务已下线。」
纪律：不写细节、不写过程，让读者3秒知道发生了什么。数字用「约」加量级，不精确到个位数装精确。

### 段2：影响面评估
写什么：影响时长、影响用户量/订单量/请求量、资损金额（直接+预估间接）、关联受影响系统、舆情与客诉量。每项没有就写「待补充」，不编。
纪律：资损口径注明计算方式（如按失败订单均值估算）；影响量给「保守/中位」区间比给单点数字可信。

### 段3：时间线
写什么：表格化——时间｜节点｜事件｜耗时。节点固定七类：发生→首次影响→发现→定位→处理动作→恢复→确认稳定。
纪律：
- 每行一个事实，不混判断（「值班查了20分钟日志」是事实；「值班能力不行」是判断，禁入时间线）
- 耗时列专门标出「从发生到发现」「从发现到定位」「从定位到恢复」三段，复盘的杠杆点就在这三段里
- 补充关键上下文行（如「21:10 变更发布完成」——与故障相关的邻近事件）

### 段4：根因归因（5Why）
写什么：归因链条（见第二部分方法）+ 根因定性。
定性四选一：
- 技术债：已知缺陷/过期设计，欠的账
- 流程缺失：本该有的流程环节不存在（变更管理/审批/演练）
- 监控盲区：故障存在但看不见，靠用户报障才发现
- 人为失误：按规程操作但出错（注意：写事实行为，不写个人评价）
纪律：一次故障常是多因复合，主次分开写；「人为失误」几乎从来不是根因，要继续问「为什么失误没有被流程拦住」。

### 段5：止损复盘（做得好与做得差）
写什么：三列——做得对的（保持项）/拖后腿的（改进项线索）/关键耗时在哪。
口径示例：「做得对：值班在30分钟内完成止损、回滚操作有记录；拖后腿：告警在影响15分钟后才被注意、值班手册无锁表处置路径；关键耗时：定位占25分钟，占故障总时长一半。」
纪律：必须同时有「做得对」列——只写差评的复盘会变成追责会，下次没人愿意快速上报。

### 段6：改进项清单
写什么：见第三部分分级方法。表格：级别｜改进项｜责任岗｜时限｜验收标准。
纪律：每条对应段4/段5的具体发现，不写「加强意识」类无法验收的项；总条数控制在3-7条，超过说明在撒网，砍到根因真正相关的。

## 二、5Why根因归因方法

### 完整链条示范
故障：线上支付回调失败2小时。
- Why1：为什么回调失败？→ 回调服务内存溢出重启，重启窗口内请求堆积。
- Why2：为什么内存溢出？→ 新上线的批量补偿功能一次性加载30天订单全量入内存。
- Why3：为什么一次性全量加载？→ 开发时用测试环境（订单量小）验证通过，未考虑生产数据量级。
- Why4：为什么测试环境与生产量级差异没被拦住？→ 上线前无性能压测环节，变更管理只卡功能验证。
- Why5：为什么压测环节缺失？→ 变更分级标准里「批处理任务」类变更未列入必压测清单。
根因定性：流程缺失（变更分级标准覆盖不全）。改进：批处理类变更纳入必压测清单 + 大数据量操作强制分页。

### 「问到哪里停」三条判断标准
1. **可行动测试**：再问一层，答案还能落到「某团队下周能开工的改进项」吗？答案是「行业现状」「人性如此」这类改不动的，停。
2. **穿越三层测试**：链条是否已从「技术层」（代码/配置）穿到「流程层」（审批/清单/演练）？技术层根因的改进项（改代码）只修这一处，流程层的改进项（改清单）修一类。至少问到流程层，但不必强问五层——故障简单时三层到根即可，硬凑五层会失真。
3. **复现测试**：如果根因不修，同样的故障还会再发生吗？答「会」说明还没到根；答「不会」可能问过了（已越过本次故障的因果链，在泛化归因）。

### 归因红线
- 不停在「人为失误」：继续问「为什么失误能到达生产/为什么没被拦截」
- 不无限上纲：问到「公司价值观」「行业通病」属于问过头，回到最近的「可行动层」
- 推断必标注：用户没给的事实线索，推断层标「待核实」，定稿前让当事人确认

## 三、改进项分级方法（止血/加固/免疫）

### 止血项（1周内，含当日）
定义：直接堵住「本次故障」暴露的洞，做完本次同类故障不再发生。
粒度：具体、小、可立即执行——盘点登记、下线任务、加一条告警规则、改一个配置。
验收标准：能当场检查的（台账齐不齐、告警响不响、任务还跑不跑）。
反面教材：「全面排查所有风险」不是止血项，是口号——排查要有具体范围和产出物。

### 加固项（1个月左右）
定义：让「同一类问题」免疫——本次的具体洞堵了，加固项确保同类的新洞不再出现。
粒度：流程/规则/工具层面的改动——变更管理补规则、值班手册补路径、调度平台加准入、发布流程加卡点。
验收标准：新流程能在下一次演练/变更中实际跑到（无审批任务真的起不来、新路径真的被值班用到）。

### 免疫项（1个季度至长期）
定义：机制性防御——不依赖人记住规则，系统结构上消灭这类故障的生存条件。
粒度：架构/设计层面的改造——阻塞式任务改非阻塞、单点改多活、人工审核改自动校验。
验收标准：以故障演练为准——注入同类故障，系统应自动降级/自动拦截/自动恢复。

### 分层自检
- 每条根因（段4）至少对应一条止血或加固项，漏了就是「根因挖了白挖」
- 只有止血没有加固，说明归因停在表层技术原因，回段4继续问
- 免疫项超过2条要警惕过度设计：本季度排不下的免疫项，明确移入技术债清单并写 revisit 时间

## 四、故障等级划分参照（P0-P4常见口径）

| 等级 | 判定要点（满足任一） | 响应口径参考 |
|---|---|---|
| P0 | 核心业务全量不可用；资损重大（百万级以上）；数据丢失/错乱；重大舆情 | 全员响应，负责人到场，分钟级通报 |
| P1 | 核心业务部分不可用（如某地域/某支付渠道）；影响用户量大（万级以上）；无资损但体验严重受损 | 值班升级，相关负责人介入，30分钟级通报 |
| P2 | 非核心业务不可用；核心业务降级但可用（如列表页降级）；影响用户量中等 | 值班处理，按需升级，小时级通报 |
| P3 | 局部小范围异常；有自动降级兜底；用户基本无感 | 值班处理，日报级同步 |
| P4 | 边缘功能异常或潜在隐患；未被用户感知即修复 | 记录在案，周报级同步 |

定级纪律：
- 按最重影响定级，不按恢复时长定级——「恢复快」不降级，「恢复慢」也不升级，影响说了算
- 两可之间就高不就低（P1/P2拿不准按P1），复盘后再修正
- 等级影响改进项资源投入：P0/P1必须配加固项，P3/P4允许只做止血
- 表中口径是行业常见参照，公司有自己的定级标准时以公司口径为准
