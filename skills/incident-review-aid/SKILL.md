# 故障复盘官

**技能定位**

用户给一段线上故障的时间线（发现-处理-恢复各节点，散记也行），输出一份标准复盘文档：故障摘要/影响面评估/时间线梳理/根因归因（5Why深挖）/止损复盘/改进项清单（短期止血+长期防复发，含责任人与时限）。比直接问模型强在三点：①六段式模板固定，产出的复盘格式与主流大厂口径一致，拿去汇报不用改骨架；②5Why归因有「问到哪里停」的判断标准，避免浅挖一层就收工、也避免无限上纲到"公司价值观"；③改进项分三级（止血/加固/免疫），每条带责任人位与时限字段，复盘会不会变成空头文章就看这一段。

**工作流程（四步）**

1. **时间线整理**：把用户散记的节点按「故障发生→首次影响→发现（谁/怎么发现）→定位→处理动作→恢复→确认稳定」排序，补齐每个节点的时间戳与耗时。缺的节点标「待补充」，让用户补——时间线断档的复盘没有价值。
2. **影响面评估**：从用户描述里提取影响维度——影响时长、影响用户量/订单量、资损金额、关联系统、舆情/客诉，对照 references/复盘模板与归因方法.md 的故障等级划分参照（P0-P4）给参考定级，最终等级由用户按公司口径拍板。
3. **5Why归因深挖**：从「直接技术原因」开始连问为什么，每层回答必须基于事实（用户给的线索或合理推断，推断的标注出来），对照方法论里的三条停止标准判断问到哪里停。产出归因链条+根因定性（技术债/流程缺失/监控盲区/人为失误四类）。
4. **改进项分级组装**：每条根因配改进项，按「止血项（1周内，堵住本次的洞）/加固项（1个月，同类问题免疫）/免疫项（长期，机制性防御）」三级分层，逐条带建议责任岗与完成时限，最后按输出格式组装全文。

**素材库说明**

- references/复盘模板与归因方法.md：四部分。①六段式复盘文档模板——各段落写什么、写多长、口径示例，组装输出时用；②5Why根因归因示例——完整链条示范+「问到哪里停」三条判断标准，第3步深挖时对照；③改进项分级方法——止血/加固/免疫三级的定义、粒度与验收标准，第4步分层时用；④故障等级划分参照——P0-P4常见口径表，第2步定级参考。

**输出格式**

```
【一、故障摘要】（3句话内：什么故障、影响多大、当前状态）

【二、影响面评估】
- 影响时长：… ｜ 影响用户/订单：… ｜ 资损：…
- 参考定级：P？（按对照表口径，最终以公司口径为准）
- 待补充：…

【三、时间线】
| 时间 | 节点 | 事件 | 耗时 |
| … | 发现 | … | 距发生X分钟 |

【四、根因归因（5Why）】
Why1：… → Why2：… → … → Why5：…
根因定性：…（四类之一）
推断标注：…（哪些层是推断，需用户核实）

【五、止损复盘】
做得对的：… ｜ 拖后腿的：… ｜ 关键耗时在哪：…

【六、改进项清单】
| 级别 | 改进项 | 责任岗 | 时限 | 验收标准 |
| 止血 | … | … | 1周内 | … |
```

## 使用示例

**输入示例**：

> 我们昨晚出事了。21:15有个定时任务把优惠券表锁了，21:20开始用户领券接口报错，值班同学21:35看到告警，查了20分钟日志没头绪，21:55有用户在群里反馈，22:00定位到锁表任务，把任务先杀了，22:05接口恢复。大概影响50分钟，领券失败估计几万次。那个定时任务是三个月前上的批量重算任务，没走变更管理，也没人知道它凌晨之外还会跑。

**输出示例（节选）**：

【一、故障摘要】定时批量重算任务锁定优惠券表，导致领券接口报错50分钟，估计影响领券失败数万次。任务为三个月前未走变更管理上线的存量任务，属「流程缺失+监控盲区」复合根因。当前已恢复，任务已下线待整改。

【三、时间线】
| 时间 | 节点 | 事件 | 耗时 |
| 21:15 | 发生 | 定时重算任务启动，锁定优惠券表 | — |
| 21:20 | 首次影响 | 领券接口开始报错 | 距发生5分钟 |
| 21:35 | 发现 | 值班同学看到告警 | 距影响15分钟（发现耗时偏长） |
| 21:35-21:55 | 定位中 | 查日志20分钟无头绪 | 定位阻塞20分钟 |
| 22:00 | 定位 | 群里用户反馈后确认锁表任务 | 从发现到定位25分钟 |
| 22:05 | 恢复 | 杀掉任务，接口恢复 | 从定位到止损5分钟 |

【四、根因归因（5Why）】
- Why1：为什么领券接口报错？→ 优惠券表被锁，请求超时。
- Why2：为什么表被锁？→ 定时重算任务21:15启动并持锁。
- Why3：为什么这个任务会在业务高峰期跑？→ 任务上线时未登记调度时间与锁范围，无变更管理审核。（推断标注：任务的调度配置细节需任务负责人核实）
- Why4：为什么未登记的任务能直接上线？→ 生产环境调度任务无准入校验，任何人可添加定时任务。
- Why5：为什么无准入校验？→ 调度平台建设时只考虑了便利性，未把生产定时任务纳入变更管理流程。
根因定性：流程缺失（主）+监控盲区（辅：锁表无专项告警，靠接口报错间接发现）。停止于Why5：根因落到「流程可落地的缺口」，再往上问会脱离本次故障的可行动范围。

【六、改进项清单】
| 级别 | 改进项 | 责任岗 | 时限 | 验收标准 |
| 止血 | 存量定时任务全量盘点登记，高峰时段（19:00-23:00）禁跑批类任务 | 运维负责人 | 3天 | 任务台账全部登记，禁跑策略生效 |
| 止血 | 锁表专项告警上线（锁等待>3秒触发） | DBA | 1周 | 演练触发一次，值班能在1分钟内收到 |
| 加固 | 调度平台接入变更管理：新建/修改任务需审批+登记锁范围 | 平台负责人 | 1个月 | 无审批任务无法启用，新增任务全带登记信息 |
| 加固 | 值班手册补「锁表类故障」处置路径：先看活跃锁清单再查日志 | 值班负责人 | 2周 | 路径写入手册，下次值班抽查使用 |
| 免疫 | 重算类任务改造为非阻塞式（分批+乐观锁），消除大表长锁模式 | 业务后端负责人 | 1个季度 | 重算任务在高峰演练不再阻塞领券 |

## 关键判定规则与常见坑

**复盘的四个动作，缺一条就不算复盘**
1. **还原时间线**：以分钟为粒度记录「发现—响应—定位—止损—恢复」五个节点的真实时刻与决策人；没有时间线的复盘会退化成情绪讨论。
2. **区分三层原因**：直接原因（触发点）→ 系统原因（为什么会放大）→ 管理原因（为什么没早发现）。**只停在直接原因等于没复盘。**
3. **改进项可验证**：每条改进项必须挂负责人、完成时间与**验收标准**（用什么指标确认已生效）；写「加强监控」这类无法验收的项视为无效项。
4. **闭环跟踪**：改进项进入任务台账逐项登记与关闭，下次复盘先核对上期改进项的落地情况。

**常见坑**
| 坑 | 后果 | 规避 |
|---|---|---|
| 追责导向 | 信息被隐瞒 | 先对事再对人，明确「不惩罚如实陈述」 |
| 归因到个人 | 同类问题复发 | 追到机制与流程层 |
| 改进项过多 | 无一落地 | 每期只保留 3–5 条高优先级 |
| 无验收标准 | 无法判断是否生效 | 每条挂可观测指标 |

## 适用边界与前置条件

- 本技能输出**复盘报告与改进项清单**，不负责组织复盘会议，也不替代运维与研发的实际处置；
- **不做责任认定与处罚建议**，不代替人力与合规的判断；
- 涉及用户数据、安全事件、监管要求的对外通报，**须由法务与合规按流程处理，本工具不生成对外口径**；
- 前置条件：需要事件时间线、系统拓扑、监控与日志片段、参与人角色；关键信息缺失时先补料再出报告。

## 进阶用法

1. **同类事件归并**：按「原因类型」而非「发生时间」归档历史事件，可发现反复出现的结构性薄弱环节。
2. **演练预案**：把复盘出的短板转成演练科目，用桌面推演验证预案是否可用。
3. **月度质量看板**：把改进项关闭率、同类复发率做成月度指标，让复盘真正进入管理循环。

## 注意事项

- 复盘文化底线：对事不对人——输出里责任岗是「岗」不是「人名」，归因链条避免指向具体个人的措辞（人为失误类根因只写事实行为，不写评价）
- 根因归因中基于推断的部分全部标注「待核实」，请用户与当事人确认后再定稿
- 改进项责任人/时限是建议值，实际排期以团队资源为准；无主无时限的改进项会退化为空话，宁可砍掉也不留悬空项
- 本工具为AI辅助生成内容，供复盘参考使用，对外通报前请按公司口径审核
